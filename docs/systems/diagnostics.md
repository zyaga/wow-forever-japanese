# Diagnostics log

> The addon's own record of problems seen in game, kept so they can be read after a reload or a crash.

## Purpose
Some failures only show in a long play session: a hooked method that stops working, a protected call the client blocks, a surface whose setup failed. A blocked call is the hardest: the block shows only the Blizzard code that tripped, often minutes after this addon's taint reached it. The taint watch (`UI/TaintWatch.lua`) records where the taint came from. Lag has the same gap: the player feels the stutter, not what ran. `Core/Perf.lua` times the addon's own work and logs the passes that took too long. The client's error window shows them once and loses them on exit. `Core/Diag.lua` writes them to the addon's third SavedVariables table, `WFJ_Log`, so they can be read afterwards, and any module can add its own entries.

## What is recorded
| Kind | When | Fields |
|---|---|---|
| `session` | each load (login or `/reload`) | client build, addon version, the surfaces whose setup failed |
| `init` | each surface whose setup failed, at load or later (a load-on-demand window) | the surface, the error (300 characters at most) |
| `blocked` | the client's `ADDON_ACTION_BLOCKED` or `ADDON_ACTION_FORBIDDEN` naming this addon | the event, the protected function (`fn`), the call stack at the block (`stack`; the client fires the event inside the blocked call), the first Blizzard Lua line in it (`site`, also in the message, so one function blocked from two paths makes two entries), whether combat was on (`combat`) |
| `context` | the first time each different block happens in a session (`events before <the block's message>`; a repeat of the same block is counted on its `blocked` entry and reads the ring no more) | the last 200 lines of the taint watch's ring before it (`events`): game events and the addon's own passes ([The taint watch](#the-taint-watch)) |
| `turned` | the taint watch: a watched field (a bar field, or one a bag item's click reads; or any field on the action bars, `reason = bar sweep`) reads as tainted for the first time since it was last clean | the field, the addon that tainted it (`by`), `reason`, `combat`, `events` |
| `write` | the taint watch: a watched field's writer left the value tainted | the field and the first stack line in the message, `by`, `stack` (the writer's whole path), `combat`, `events` |
| `taint` | after each different block of a session (`reason = block <the block's message>`), once combat is over, and on `/wfj taint` (`reason = slash`); the reason is in the message too, so each block's scan is its own entry | every field that reads as tainted under the bar, Edit Mode, tracker, tooltip, spellbook, quest log, quest list (its pooled rows too), map, bag, merchant, bank and stack split frames, and under every frame the addon's declarations resolved to, with the addon that did it (`fields`), the globals this addon tainted (`globals`), `checked` |
| `hook` | a method the addon post-hooked on one frame (`Diag.watch`) no longer reads as a function, or is another function than the hook the addon left there (`seen = replaced`) | frame, method, what it reads as, its type on the frame's own table and on what the frame inherits |
| `font` | message `dialogueui tag face`: the frame after a Dialogue UI quest tag got its Japanese, the tag no longer wears the bundled face (its Japanese would show as empty boxes); the face goes back on | the face's path, size and flags, and the font object it follows |
| `speech` | an NPC's chat line (`CHAT_MSG_MONSTER*`, `CHAT_MSG_RAID_BOSS*`) that ships Japanese was left English, or its English could not be read | the reason (the message, below), `event`, the chat frame (`frame`), the line's gossip key (`key`, 16 hex characters; absent when the English could not be read) |
| `speechline` | every NPC chat line (`CHAT_MSG_MONSTER*`, `CHAT_MSG_RAID_BOSS*`), translated or not, so one sighting in play says why a line stayed English | the outcome and the key as the message (`translated`, `no Japanese` when no Japanese ships under the key, or the first `speech` reason), `event`, `frame`, `key`, `shipped` (Japanese ships under that key), `translated` (the line was rewritten with its Japanese), `hasToken` (the English still has the speaker's `%s`), `speakerInText` (the speaker's name is written into the English; `none` or `secret` when there is no readable speaker), `speakerKey` and `speakerKeyShipped` (the key with the name put back as `%s`, and whether Japanese ships under it); `target` (who the line is said to: `none`, `me`, `other` or `secret`), with `targetSep`, `targetSpace` and `targetStartsMe` (whether the target name holds the surname separator or a space, and whether it starts with this character's name), `meSep` and `meSurname` (whether `UnitName("player")` holds the separator or returns a surname: Forever characters have one), `collector` (what the English collector answered for the line, with its reason, or `not asked` when the line was said to someone else, names a party member, or is in an unknown language), and `other` (`target` or `party` when the line's Japanese was found under another player's name, from the line's target (its first name or the whole target) or from a party member named in it; the line's `key` is then the shipped row's, which holds no name; a line that names another player with no row found has no `key` or `speakerKey`, since both would be hashes of English holding that name); flags only, never a name; `english` (`none`, `secret` or a type) when the English cannot be read. One entry per outcome and key per session |
| `slow` | one of the addon's timed passes took 8 ms or more in one frame, all its calls in that frame added up ([Timing the addon's own work](#timing-the-addons-own-work)) | the label as the message (one of the labels in the table below), `ms` (the frame total, to a tenth), `kb` (the Lua memory allocated in that frame), `calls` (how many calls in that frame). A repeat raises `n` and keeps the largest `ms` with its `kb` and `calls` |
| `perf` | at logout (so also on `/reload`), message `session totals` | `rows`: every timed or counted label of the session, one `label calls ms max kb` part each (total ms and longest call in ms to a tenth, KB allocated), most total time first, joined by ` \| ` |
| `memory` | every 5 minutes | the Lua memory |

Every entry also carries the local time (`at`), seconds since the client started (`up`) and the Lua memory in KB (`memKB`). The same kind and message again in one session adds to that entry's count (`n`) and last time (`last`) instead of a new entry, so something repeating every few seconds never pushes the rest out. The log keeps 500 entries: over that, the oldest memory sample goes first, then the oldest `slow` or `perf` entry (a session adds one per slow label and one set of totals, and blocks and taint are rarer), then the oldest `speechline` while there are more than 100 (one per NPC line, so the most numerous), then the oldest problem, then the oldest `speechline`, then the oldest session (so a log full of problems still keeps the latest NPC lines), and it never keeps more than 50 sessions.

A `speech` entry's message is one reason per exit of the chat hook (`Speech.onAddMessage`):

| Reason | What happened |
|---|---|
| `not hooked` | logged once at load, not per line: the speech hook was not set up, so no NPC line is translated or traced; `missing` names what was not ready (`frames`, `chat types`, `key` or `ChatSystem`) |
| `unknown chat type` | the line's chat type id is not one the addon knows |
| `no line` | no chat frame or no line text was passed |
| `no eventArgs` | the client passed no event arguments |
| `no formatter` | the client passed no function to rebuild the line |
| `no TransformMessages` | the chat frame has no `TransformMessages` |
| `no English` | the event's English is missing or empty |
| `secret text` | the English or the line is a secret value |
| `NPC talk off` | the player turned NPC talk off |
| `translation refused` | the line ships Japanese but `Speech.translate` refused it (for example its `%s` count differs from the English); the prefix ("says:") is still translated |
| `formatter error` | the client's formatter failed on the Japanese; the prefix is still translated |
| `line unchanged` | the line came out the same as the English |
| `remember refused` | the chat history store refused the line |
| `no line matched` | the history filter matched no line; the line still counts as handled |

An entry is written only when the line's English has a shipped gossip row (status `.`, non-empty Japanese), or when the English cannot be read at all. A line with no translation is never logged. With the usual dedup, each reason is one entry per session, with its count in `n`. Boss emotes in the middle of the screen and chat bubbles are not logged. A chat frame whose `AddMessage` was never hooked logs nothing here; a hook that was lost is already a `hook` entry.

A `hook` or `blocked` entry also prints one chat line, once per session, ending in "/wfj log shows it".

## The addon's own Lua errors
Forever hides Lua errors by default, so a player never sees an error in this addon's code. `Core/ErrorLog.lua` keeps them in the same table, under `WFJ_Log.errors`, for a bug report ([fix reports](fix-reports.md), "Bug and idea reports"; [ADR-057](../adr/057-catching-the-addons-own-lua-errors.md)).

- **How it catches them.** `Core/ErrorLog.lua` is the first file in the TOC, so it catches load errors in every other file. At load it reads the client's current error handler (`geterrorhandler`) and sets a wrapper (`seterrorhandler`). The wrapper records the error inside `pcall` and then always calls the previous handler with the same arguments, so the game's Lua error window, BugSack and other addons see every error as before. An error raised while recording is never recorded again.
- **Errors a setup step catches.** A setup step in `Main.lua` runs inside its own `pcall` (the step guard), so its error never reaches the handler. The guard hands it to `ErrorLog.recordCaught`, which keeps it the same way, from the message alone (no stack is left to read).
- **The stack.** `ErrorLog.stack` reads it the way the client's own handler (`Blizzard_ScriptErrors.lua`) does: the current callstack height less the error's. Because that level comes from the error's own height, the extra wrapper frame does not change what the client prints. A handler called directly, outside an error, has no error height and uses offset 0, as the client does. On a client without the height functions there is no stack, and the message alone decides. The wrapper's own `Core/ErrorLog.lua` frames are left out of the stored stack.
- **Only errors raised in this addon's files.** An error is kept only when it was raised in a file under `WoWForeverJapanese/`. The file that decides is the one the message names at its start (`path:line:` or `[string "..."]:line:`). For a message without one, it is the top Lua frame of the stack, skipping `[C]` frames, `(tail call)` and the wrapper's own frames. A path counts as ours when `ForeverJapanese/` (or `\`) follows `WoW` after a `/`, `\`, `@` or the start, or follows the client's front-truncated form, as in `...rface/AddOns/WoWForeverJapanese/UI/MinimapButton.lua:144:`. An error whose message names another addon's or Blizzard's file is not ours, even when this addon's code is lower in the stack. A `/run error("x")` typed in chat names `[string "..."]` and is not kept. A value the client marks as secret (`canaccessvalue`) is not read.
- **What is stored.** Each entry holds `msg` (500 bytes at most, cut on a UTF-8 boundary), `stack` (12 lines and 1,000 bytes at most), `n` (how often), `first` and `last` (local time) and `sent`. No local variables. The same error again adds to `n` and moves `last`. For matching, table, function, userdata and thread addresses in the message are blanked, so the same error raised on another table is one entry. A repeat of an error already sent starts over as a new one: `sent` is cleared, `n` is 1 and `first` restarts.
- **Cap.** 30 errors. Over that, the oldest sent error goes first. With none sent, the newest is dropped, so the first errors (most often the cause of the rest) are kept.
- **The player's name.** Written as `<name>` wherever it appears as a whole word in a message or stack, before the message is cut to length. A name that is a file name in a path (`/Main.lua`) is left alone, since the report needs the file. The scrub runs again at `PLAYER_ENTERING_WORLD` for an error caught before the name was known.
- **Before the log loads.** Errors caught before `WFJ_Log` loads are held in memory and merged when it loads: a repeat adds its count and keeps the later time, and an entry caught before the clock was set up gets the load time (the clock reads the time once the `compat` step has run; a time it still cannot read shows as `?` in a bug report). A saved entry that is not a table with a string message is dropped at load.
- **Chat line.** The first error stored in a session prints one line: `WFJ: the addon hit a Lua error. /wfj bug reports it.`
- **No setting.** Nothing turns capture on or off.

**Another error addon.** BugGrabber (the part of BugSack that catches errors) sets its own handler, never calls the one before it, and then makes `seterrorhandler` do nothing. `!BugGrabber` loads before this addon. With it present this addon's wrapper sees no errors. At `PLAYER_ENTERING_WORLD`, once every addon has loaded, `ErrorLog.checkOurs` compares the active handler with the wrapper. When they differ (and none of this addon's errors reached the wrapper this session), the report window's bug summary says another addon catches Lua errors and asks the player to paste this addon's errors from it. The addon never reads BugGrabber's store: that would be a dependency on another addon.

## The taint watch
`UI/TaintWatch.lua`, always on, read-only ([ADR-058](../adr/058-text-blizzard-measures-on-a-protected-path-stays-untouched.md)). The client's `issecurevariable(table, key)` tells whether a field was last written by tainted code, and by which addon; the watch asks it about the fields Blizzard's bar layout and a bag item's click read:

- **Watched fields:** `showAllButtons` on the twelve action bars, `snappedToFrame` on the bars and the XP bar containers, the totem bar's `inMainActionBarState`, the quest tracker's `topModulePadding`, and the globals `ON_BAR_HIGHLIGHT_MARKS` and `PET_ACTION_HIGHLIGHT_MARKS`. Checked every 2 seconds; the first time one turns tainted it is a `turned` entry.
- **The bag click:** a bag item's right-click (`ContainerFrameItemButton_OnClick`, Forever 1.60.1.70790 `mainline/containerframe.lua:1503–1611`) reads a set of globals before it calls `C_Container.UseContainerItem`. One of them tainted turns the use into a forbidden call, out of combat too. They are on the field list (`BAG_CLICK_GLOBALS`, 35 names): the click handler itself, the merchant, bank, guild bank, mail, auction, trade and stack split frames and the other windows it checks, the `C_Container`, `C_Cursor`, `C_Item` and related namespaces, the cursor functions, the merchant confirm and refund functions and `StaticPopup_Show`; and three `MerchantFrame` fields (`BAG_CLICK_MERCHANT`: `selectedTab`, `extendedCost`, `highPrice`; `refundItem` is cleared by the click's own first call, so it is left out). Checked with the bar fields every 2 seconds, so the first to turn tainted is a `turned` entry with the events before it.
- **Their writers:** a post-hook on `SetShowGrid`, `SetSnappedToFrame` / `ClearFrameSnap`, `MainActionBarStateOverridden`, `UpdateTopPadding`, the highlight-mark functions and `PetActionBar`'s mark methods. The hook only reads; when the value comes out tainted it is a `write` entry with the stack.
- **The tracker's update queue:** a post-hook on `ObjectiveTrackerFrame:MarkDirty` (hooked once `Blizzard_ObjectiveTracker` has loaded). `MarkDirty` sets `dirty` and queues the tracker update with `RunNextFrame`, which runs that update with the caller's taint; a module's `MarkDirty` goes through the container's (`mixinutil.lua:346–352`, `blizzard_objectivetrackermodule.lua:86–90`). When `dirty` comes out tainted it is a `write` entry labelled `ObjectiveTrackerFrame.dirty`, and its stack names the code that queued a tainted tracker update.
- **The quest log and the click path:** a post-hook on `WorldMapFrame:SetMapID` logs a `write` entry `WorldMapFrame.mapID` when the zone the world map shows comes out tainted (the map's quest pins compare it before their protected call, blizzard_mapcanvas.lua:60-65); a post-hook on `QuestMapFrame_ShowQuestDetails` logs a `write` entry `QuestMapFrame.DetailsFrame.questID` when the stored quest id comes out tainted (the quest log reads it again on its next refresh, on the way to the map's quest pins); a post-hook on `QuestObjectiveTracker` / `CampaignQuestObjectiveTracker`'s `OnBlockHeaderClick` logs any of the clicked block's or its module's keys (`OnBlockHeaderClick`, `OnHeaderClick`, `id`, `parentModule`) that read as tainted, and the rest of what the click reads before it opens the quest log: the title button's `OnClick` method, the globals it calls (`ChatFrameUtil` and its two link functions, `IsModifiedClick`, `GetQuestLink`, `QuestUtil`, `QuestCache`, `C_QuestLog`, `QuestMapFrame_OpenToQuestDetails`, `ShowQuestComplete`) and the quest's `QuestCache` entry with the fields the click reads (`isAutoComplete`, `IsComplete`, `CheckRefresh`, `GetID`, `questID`, `hasQuestLogInfo`). A title click that runs tainted with none of these flagged points at a read not yet listed. The block-time scan also walks `QuestMapFrame`, `QuestScrollFrame`, `WorldMapFrame` and `QuestCache`, and walks deeper where the data sits (`SCAN_DEEP`: the tracker 5 levels, down to its pooled quest blocks; array entries are walked, only named fields are checked). These found the cause of `ADDON_ACTION_BLOCKED Button:SetPassThroughButtons()` on a tracked quest title clicked in combat on 1.60.1.70790: the quest list resized and laid out by the addon ([ADR-069](../adr/069-unit-menus-and-edit-mode-stay-english.md)).
- **Bar sweep:** once a minute out of combat (every 30th field check, `SWEEP_EVERY`), any field on the action bars that newly reads as tainted, for fields not on the list. A sweep walks every action bar (about 6 ms, measured in game); every 10 seconds it was a felt hitch, and the taint it looks for builds up and stays, so waiting a minute loses nothing.
- **Events and the trail:** a ring of the last 200 lines, saved with the first `write` of each writer, each `turned` entry and the first time of each different block. It holds game events (with `ShowUIPanel` / `HideUIPanel`; frequent ones left out) and the addon's own passes: each frame in which the addon's timed passes ran ([Timing the addon's own work](#timing-the-addons-own-work)) adds one `wfj <labels>` line, its labels in the order they ran, so a block or a taint shows which of the addon's surfaces ran just before it. The `idle.*` labels stay out of it (they run on nearly every event and frame and would halve the ring's history); they stay in the totals and the `slow` log. The line goes in when that frame has ended and the next line is written (a game event, another frame's line), so the ring keeps the order things ran in; when the ring is read for a block, the frame still running goes in too. The same line again with nothing between is counted on that line (`wfj tooltip.item tooltip.GameTooltip ×12`: a hovered item refreshing). The voice panel's whole-text control no longer calls Blizzard's quest log, so the `wfj voice.openQuestLog` line is gone: that call was the first tainted write a trace found before a blocked world map in combat ([Client limits](../architecture/client-limits.md)).
- **Scan:** after each different block of a session, once combat is over (it walks every global, too heavy for a fight; a tainted value stays tainted until it is rewritten), and on `/wfj taint`. Blocks are told apart by the block entry's message, which names the protected function and the first Blizzard line: different blocks can have different writers, so each gets its own scan, and a repeat of a block already scanned queues none. The scan walks the bar, Edit Mode, tracker, tooltip, spellbook, quest log, quest list and map frames; the bag frames (`ContainerFrame1` to `ContainerFrame13`, `ContainerFrameCombinedBags`: a bag item's click reads its button's fields, `ContainerFrame<n>.Items[i].bagID`, `mainline/containerframe.lua:1845–1847`), `MerchantFrame`, `BankFrame` and `StackSplitFrame`; the quest popup's and the quest window's scroll frames (`QuestLogPopupDetailFrameScrollFrame`, `QuestDetailScrollFrame`, `QuestProgressScrollFrame`, `QuestRewardScrollFrame`, `QuestGreetingScrollFrame`: the client's next `ScrollToBegin` reads their scroll bar, [ADR-077](../adr/077-the-quest-windows-are-never-re-measured-from-addon-code.md)); and every table the addon's `Compat` declarations resolved to (`Compat.tables()`, labelled `surface.key`: the Blizzard frames the addon touches), their own fields and one level down, listing only fields this addon tainted (those frames hold other addons' and the player's keys too).

Its cost is a few dozen `issecurevariable` calls every 2 seconds (38 of them for the bag click), one table write per game event, and one per frame of the addon's passes that does not repeat the line before. A tainted writer that runs again is only counted: its stack and events are kept from the first time. Nothing turns it off.

## Timing the addon's own work
`Core/Perf.lua`, on unless switched off for the session (`/wfj perf off`). It is pure: `Main` injects the clock (`debugprofilestop`, milliseconds), the Lua memory (`collectgarbage("count")`, KB), the frame stamp (`GetTime`, the same all through one frame) and the trail (`TaintWatch.trail`). It times the addon's central write paths and the work that runs with no window open, each under a label. `Perf.call(label, fn, ...)` times one call and returns `fn`'s first result; `Perf.wrap(label, fn)` gives a timed copy of `fn` for a script handler or a ticker; `Perf.count(label)` counts an event, at next to no time of its own.

| Label | What it times |
|---|---|
| the surface name the call carries | `Render.show` and `Labels.show`: every line the addon writes into a window |
| `help` | `HelpTooltip.walk`, `walkAs` and `appended`: the tooltip walks that match lines to the client's own strings |
| `refresh` | `Render.refresh`: every open line again when the reveal key, a setting or the master switch changes |
| `tooltip.<kind>` | a tooltip pass that runs (`item`, `spell`, `aura`, `compare`: only when the tooltip is one of the addon's; `currency`, `mount`, `pet`, `set`, `lock`, `totem`, `party`, `flyout`: each `TooltipData` post-call) |
| `tooltip.item.read`, `.collector`, `.sets`, `.structural` | the parts of a full item pass: reading the tooltip's lines, recording the English, the set bonuses, the lines matched to the client's own strings |
| `tooltip.item.reused`, `tooltip.item.full` | counts: an item pass that only put the Japanese back on a rebuild with the same lines, and one that ran in full ([Tooltip rebuilds](../architecture/addon-modules.md#tooltip-rebuilds)) |
| `tooltip.compare.reused`, `.unchanged`, `.full` | counts: a comparison pass that put the Japanese back, one that found the tooltip shown again with nothing new, and one that ran in full |
| `tooltip.refit` | the two `Show()` calls that redraw a tooltip after its lines changed: the client's own tooltip code runs again inside them |
| `tooltip.release` | a tooltip's `OnHide` cleanup: its records restored and dropped |
| `idle.watch.event`, `idle.watch.tick` | the taint watch: its handler on every game event, and its 2 second timer (the field checks and the bar sweep) |
| `idle.main.event`, `idle.diag.tick` | `Main`'s event handler and the log's own timer (the hook checks and the memory sample) |
| `idle.study.tick`, `idle.textwatch`, `idle.dialogueui.event`, `idle.voicepanel.event`, `idle.voiceplayer.event` | the study tab's timer, the text watch's per-frame check, and the Dialogue UI, voice panel and voice player event handlers |

The `idle.*` labels are the work that runs whether or not any window is open, so a stutter with nothing on screen can be traced too. The taint watch turns its noisy events away before timing, so `idle.watch.event` counts only the events it keeps.

- Each call's time and the Lua memory it allocated (0 when the collector ran during the call) are added to its label's total for the current frame and for the session. A count adds one call and next to no time. Only the outermost call of a label counts, so a walk inside a walk is counted once. A call that raised and never closed is set aside at the label's next call in a later frame.
- Nothing runs on its own. When the first timed call of a later frame ends, the frame before is looked at: each label whose total reached `Perf.SLOW_MS` (8 ms, half of a 60 fps frame) is one `slow` entry. A label under it logs nothing.
- Each frame's labels go to the taint watch's ring as one line (above). The trail and the `slow` log are guarded: a failure there never reaches the write that was timed. On logout the last frame is looked at too, and then the session's totals are one `perf` entry (`session totals`, every label), so a `/reload` is all it takes to keep them.
- The timed functions return exactly what they returned before. They call `WFJ.Perf` directly: it loads before every surface (the specs load it first too), and without its clock it does nothing. Nothing is allocated per call.
- `/wfj perf off` takes the clock away for the rest of the session: every timed call is a plain call, nothing is logged or added to the ring, so the addon can be measured with no timing at all. `/wfj perf on` brings it back. It is not saved: a `/reload` turns timing on again.

`/wfj perf` prints the session's 10 labels with the most total time (`/wfj perf <n>`: the top n), one line each: label, calls, total ms, longest single call in ms, KB allocated (`perf: nothing timed yet` before any call). `/wfj perf reset` clears the session totals and prints `perf: totals cleared`; `slow` entries already in the log stay.

**Tracing lag.** `/reload` after the stutter and read the `slow` entries and the `perf` entry (`/wfj log 30`): a `slow` label names the surface, tooltip pass or idle handler, `ms` how long it took in its worst frame, and `calls` whether that was one slow call or many cheap ones; the `perf` rows give the whole session, counts included (how often the client rebuilt a tooltip, how often the addon reused its last pass). `/wfj perf` gives the session's totals so far.

## Tracing a blocked action
1. **Read the block.** `/reload`, then read `WFJ_Log` (or `/wfj log 30`). The `blocked` entry's stack is the Blizzard path that tripped: the reader, never the cause.
2. **Find the first taint.** The earliest `turned` and `write` entries of that session, before the block, name the field and the writer's stack. A `write` stack that runs through this addon's file names the line to fix. The `wfj <label>` lines in the block's `events` name the addon's passes that ran just before it.
3. **If the stack is all Blizzard code,** the taint came in through something that code read just before writing. The `taint` scan lists what was tainted; add a probe on the writer of that value (a post-hook that logs `debugstack()` when the value comes out tainted, as `TaintWatch.wrote` does) and repeat one level up. A field that is clean at one line and tainted a few lines later points at what the code read in between (the spellbook case: FontString measurements, [ADR-058](../adr/058-text-blizzard-measures-on-a-protected-path-stays-untouched.md)).
4. **Prove the fix in game** with the same steps that blocked, and read the log: no `turned`, no `write`, no `blocked`.

Never turn on the client's `taintLog` on Forever: it makes every post-hooked method fail when Blizzard calls it ([Client limits](../architecture/client-limits.md)).

## Adding to it
`WFJ.Diag.log(kind, message, fields)` from any module. `fields` holds strings, numbers and booleans; anything else is stored as its type name. `WFJ.Diag.watch(frame, method, label)` after a `hooksecurefunc` on a single frame adds that hook to the checks (every 5 seconds).

Watched now: chat frames' `AddMessage` (`UI/Speech`), chat edit boxes' `UpdateHeader` (`UI/ChatTabs`), the XP bars' `UpdateCurrentText` (`UI/MicroMenu`), gamepad prompts' `SetPromptText` (`UI/Gamepad`).

## Reading it
- In game: `/wfj log` prints the last 10 entries, `/wfj log 30` the last 30 (at most 50), then one line with the Lua errors: `errors: N recorded, M not sent (/wfj bug)`. `/wfj taint` runs the taint scan now and says how many tainted fields and globals it found. `/wfj perf [n]` prints the slowest timed passes this session; `/wfj perf reset` clears them; `/wfj perf off` and `/wfj perf on` switch timing off and on until the next reload.
- After the session: `WTF/Account/<ACCOUNT>/SavedVariables/WoWForeverJapanese.lua`, the `WFJ_Log` table. The client writes it on logout, `/reload` and exit, not on a crash.

## Privacy
No game text, no character, realm or account name, no chat, no location. Frame and function names, counts and times only. A `speech` or `speechline` entry names the line by its gossip key, a hash of its English ([ADR-005](../adr/005-gossip-key-fingerprint.md)), never by its text or the speaker's name. The taint watch's event ring keeps an event's first argument only when it is a number, a unit token (`player`, `party2`, `nameplate14`, `targettarget`) or the addon name of `ADDON_LOADED`, never other text (another event's first argument may be a player's name), never a secret value, and leaves every chat event out. A `write` entry names the first line of its stack outside this addon, the Blizzard writer. A `slow` entry, the `perf` entry and a `wfj <label>` line in the ring keep labels, counts, times and memory only: they name a surface, a tooltip pass or an idle handler, never a tooltip's or a window's text. The tooltip pass keeps its last lines' English in memory to tell a rebuild with the same lines; that is never written to the log or saved. A stored Lua error holds the error's own message and stack, with the player's name written as `<name>`; stack paths start at `Interface/AddOns/`, never the account folder.
