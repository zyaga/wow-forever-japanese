# Addon modules

> Module boundaries inside `addon/WoWForeverJapanese/`, the dependency direction, and the render mechanism. The addon targets the Forever client only ([ADR-034](../adr/034-forever-is-the-only-target.md)): every module resolves Forever's names, with no client check. The rules the modules follow are in [Principles](principles.md). Decisions: ADR-002/004/005/007/008/009/010/011/013/015/016/017/018/019/022/024/025/029/031/034/035/036/037/038/039/040/041/042/043/044/045.

## Purpose
Each Blizzard frame is touched in exactly one file; the policy "what should this element show now" and the capture/apply/restore state machine are pure and unit-tested; a new surface or setting is one file / one registry line; every client-specific name resolves through one compatibility file.

Arrows point inward: UI → Core → Data. `Core/*` never mentions `CreateFrame`, `_G[...]`, or a frame global; a CI grep asserts it ([principle 8](principles.md#8-rendering-apart-from-data), made mechanical). `Core/Compat.lua` passes that gate by reaching the world only through an `env(name)` function Main injects; the frame-name candidate lists it resolves live in the surface files, not in `Core/`. `Core/State.lua` is the only channel back to UI (a 50-line pub/sub).

### Surfaces fail independently (ADR-025)
The load sequence is the addon's one shared failure point: `Main.OnLoad` runs many `init` calls. Unguarded, one throwing would take every later one down with it, `Slash.register` and so `/wfj` itself included ([Forever client differences](../research/2026-09-17-forever-client-differences.md), finding 2).

Every step of `OnLoad` runs through one local `step(name, fn)` in `Main.lua`: it `pcall`s `fn`, and on failure appends `{ surface = name, err = tostring(err) }` to `WFJ.initErrors` and returns `nil`. It wraps `Compat.init`, `Settings.load`, `Collector.load`, `BuildUIIndex`, `Render.init`, `Modifier.refresh`, `ButtonText` / `HelpTooltip` / `LoadOnDemand`, every `Labels.forbidNames` call, every surface `init`, `Scan.init`, `Slash.register` and `AddonListButton.install`. The `pcall` around `Compat.registerOptions(Options.build())` keeps its own `WFJ.Options.buildError` field (the settings surface reads it) **and** records into `WFJ.initErrors` like everything else.

Three properties are the contract, pinned by `tests/lua/spec/init_guard_spec.lua`:
- **The guard wraps, it does not reorder.** `ButtonText` / `HelpTooltip` / `LoadOnDemand` precede the surfaces; `Labels.forbidNames` precedes each window's `init`.
- **One broken surface costs that surface and nothing else**: every later `init`, the options registration, the AddOn List button and `Slash.register` still run.
- **The failure is reported, not swallowed.** `/wfj debug` prints `surface errors: <surface>: <err> · …`, and `none` on a clean load. Together with the existing `unresolved widgets:` line that is the whole compatibility report on a new client, without re-running the survey.

The guard covers the **load sequence only**. A hook that installs fine and raises later, inside a client call, is still an ordinary Lua error on that path.

### Forever frames per surface (ADR-029; the only target, ADR-034)
Forever's game type `camelot` is a member of the **mainline family** (`[Family]` = `Mainline\`, `[Game]` = `Camelot\` in its TOCs): it runs the retail UI with camelot overrides, so the Classic frames are never created there. Evidence per surface: [camelot surface re-target](../research/2026-09-19-camelot-surface-retarget.md). Each surface resolves Forever's names only:

- **Candidates are Forever's names.** Every name is declared through `Compat` as the camelot global or a **dotted path** (`PlayerSpellsFrame.TitleContainer.TitleText`; `Compat`'s lookup walks any depth); a declaration stays a list even with one name. A hook is installed only for a writer that resolves. There is no client check.
- **Hook the writer's shape.** A global function → `hooksecurefunc(name)`. A mixin method called as `self:…()` → `hooksecurefunc(frame, "Method")` on the instance. A method camelot registers **by function reference** (a frame hook never sees that call) → hook what it calls by method lookup, or its `EventRegistry` event. A Menu entry whose initializer closes over the English → `Menu.ModifyMenu`. A load-on-demand addon → `LoadOnDemand.when`, either load order.
- **Pools are walked after the writer**, or followed with `ScrollUtil.AddInitializedFrameCallback`; a row's record is keyed by a stable id (`questID`, `block.id`, the spell slot) or by the row widget, never by position.
- **Everything by type.** A resolved value is used only as the type the code needs: a function called only when `type(fn) == "function"`, a widget used only with `GetText` / `SetText` functions, so a name moved into a namespace table degrades to English.
- **`/wfj debug`'s unresolved list** is grouped by surface; an entry there is a real gap (or a name kept until an in-game check places it, ADR-034).

## The render mechanism (ADR-002 made concrete)
Some citations below point at the Classic Era client source, where the mechanism was first designed; they are kept as evidence. The addon targets Forever only; each surface's Forever writer is in the table above and in its module's header comment.

1. **Read English from the API, not the widget.** Quest windows: `GetTitleText/GetQuestText/GetObjectiveText/GetProgressText/GetRewardText` [verified: classic_era FrameXML; the same getters Blizzard's writers call, `Vanilla/QuestInfo.lua:126–166, 328–350`, `Classic/QuestFrame.lua:200–222`]; quest map details and popup: `C_QuestLog.GetTitleForQuestID(C_QuestLog.GetSelectedQuest())` (title) + `GetQuestLogQuestText()` → `description, objectives` (the readers `UI/QuestMap.lua` declares); gossip: `C_GossipInfo.GetText()` (greeting) and, per option row, the `GetOptions()` entry the client wrote it from (`elementData.info.name`) [verified: classic_era 1.15.9 `Shared/GossipFrameShared.lua:236–294`]; quest greeting prose: `GetGreetingText()` [verified: `Classic/QuestFrame.lua:305–317`]. Tooltips are the documented exception: the lines are only reachable as the `<FrameName>TextLeft<n>` FontStrings (`GameTooltipTextLeft2` …), so `UI/Tooltip` reads the widget: the lines *are* the English, and the run's texts are also the align gate's scope (`ctx.lines`), guarded by the re-entrancy check and the in-refit flag.
2. **Feed the Collector, then capture.** The surface passes the API English (tooltips: the run texts / `GetSpellDescription`) to `Collector.record`; gossip lines to `Collector.recordGossip` with the NPC's GUID, before any guard or render, independent of the master switch, areas and modifier; then capture into a render record keyed by the logical element.
3. **Apply** (`Render.show`): `Translator.resolve` → `apply` ⇒ `SetFont(bundled, same size/flags)`, `SetText(ja)`: `ja` has had the player tokens expanded (`{name}` / `{class}` / `{race}` / `<a/b>`) inside `resolve`, after the align gate and before the write; the expansion is deterministic within a session, so `Render.refresh` finds nothing to rewrite; `none` ⇒ the widget is left as the client wrote it; the marker messages go to the surface's banner (or inline when it has none, see Markers below); tooltips then `ctx.refit()` (`frame:Show()`): once per description run, not per line: the surface holds the in-refit flag while it shows the run, so the per-record refits are no-ops, then calls it once; a `Show()` that re-fires the tooltip's post-call returns immediately under the same flag.
4. **Restore / reapply** (`Render.refresh`) on `State` events `modifier`, `enabled`/`area`, and `markers` for every *open* surface; a write happens only when the desired text differs from what is applied. Missing/rejected entries are captured but never written (unless `marker.missing` is on: then the live English gets the suffix, in its original font), so the frame is untouched by construction (one mechanism for fallback and modifier).
5. **Release** on the frame's `OnHide`: the superset of every close path (`QUEST_FINISHED → HideUIPanel(QuestFrame) → OnHide`, Esc, accept, decline, the log's close button). Quest windows: `QuestFrame:HookScript("OnHide", …)`; quest map: each of its frames' `OnHide`; gossip: `GossipFrame:HookScript("OnHide", …)` (`GOSSIP_CLOSED` reaches it through `HideUIPanel` [verified: `Classic/GossipFrame.lua:13–24`]), and a pooled row's records are also dropped on `OnReleasedFrame`, before the pool reuses the row; the quest greeting prose is released with `QuestFrame`; tooltips: each frame's `OnHide` releases its own surface. Records die with the frame.
6. **Write after the client's writer, by hooking the writer.** A surface `hooksecurefunc`s the client function that writes the text it translates (`QuestInfo_Display` for quests: called by name from Lua, so the global is resolved at call time), so our write follows the client's by construction: no timer, no dependence on event dispatch order (ADR-009). **Frame-script exception:** a writer bound in XML by `<OnShow function="…"/>` (`QuestFrameProgressPanel_OnShow`) is held by the frame as a function *value* and reached only through `panel:Show()`; `hooksecurefunc` on the global `[likely]` would not run (unverified in-game), so it is hooked with `panel:HookScript("OnShow", …)` instead [verified: classic_era `Vanilla/QuestFrame.xml:267`, `Classic/QuestFrame.lua:81–82`]. `hooksecurefunc` is in live use by the predecessor on 1.15.5 (`CQJT.lua:651`, on `SelectQuestLogEntry`), and `QuestFrame.xml` / `QuestLogFrame.xml` declare no `protected="true"`; no taint path. A deferred tick (`C_Timer.After(0, …)`) is the **fallback only** for a surface whose writer cannot be hooked; the quest surfaces do not use one (the predecessor's 0.1 s wait came from hooking `SelectQuestLogEntry`, which runs *before* the writer in the same call chain).
7. **Equality guard, and the drop rule.** Per field the surface reads the API English and the target FontString; the field is shown only when `fs` resolves, `en` is non-nil and non-empty, and `fs:GetText() == en` (ADR-009). An empty `""` English is skipped like a mismatch: no record, no write, no missing marker. This is what keeps a decorated widget (a failed quest's log title carrying the localised `FAILED` string, `" - (Failed)"` in enUS), a moved widget, or an ordering surprise from ever being overwritten: the safe failure is "frame untouched". **A skipped field's stale record is dropped** (`SurfaceState.drop`): the client's English is put back only if our text is still on the widget, otherwise only the font is reset; our old Japanese is never restored over text the client has since written, and a later Alt press / release writes nothing for it. A surface whose id goes to `0` / `nil`, or a quest-window panel giving way to another, is forgotten whole (`Render.forget`). Refit after a write is `<scroll frame>:UpdateScrollChildRect()`; the panels are anchor-chained, so element positions follow the new text height without re-running the writer.

8. **Readings follow the apply** ([ADR-036](../adr/036-readings-hover-word-lists.md)). An applied record on a quest or gossip prose surface (or a plain-text book page, through `UI/ItemText`'s own FontString, [ADR-044](../adr/044-area-text-and-book-word-cards.md)), or a `ui` label record on a window surface whose FontString is not a button's text or inside a protected frame ([ADR-041](../adr/041-word-cards-on-window-labels.md)), gets a cover frame from `UI/Readings`; a restore (Alt held, master switch or area off, missing translation) detaches it first, so the word-reading box can never show over English. Word rectangles are measured on mouse enter only, through the one guarded span call ([Readings → The guard](../systems/readings.md#the-guard)).
9. **Recent lines follow the apply** ([ADR-045](../adr/045-player-fix-reports.md)). `UI/Render`'s local `sync(rec, fromShow)` calls its local `noteRecent(rec, text, fromShow)` right after `SS.apply` when the record's own action is `apply`: a primary record showing its Japanese (`desired` returns the action; a companion's blank reports `follow`). A write that comes from `Render.show` records the line every time; a refresh records a record only the first time it applies it, so a refresh never reorders the list. It passes `rec.meta.kind`, `rec.meta.id`, the surface, the written text (for `shown`) and `GetTime()` (for bursts) to `RecentLines.note` under `pcall`; a failure counts in `Render.recentErrors` and never stops the write. Restores, `leave` / `none` and companions record nothing. Every `Render.show` caller and the kinds it passes are pinned in `recent_lines_spec.lua` ([Fix reports → Recent lines](../systems/fix-reports.md#recent-lines)).

**Fresh-launch font loading** [verified in game, Classic Era 1.15.9.69722; see [the lesson](../lessons/2026-09-14-bundled-font-refused-on-fresh-launch.md)]: on a fresh client launch (not `/reload`), `FontString:SetFont(<bundled ipagui.ttf>, …)` returns `false` for every widget the addon touches at load: 194 refusals on the window modules' load-time labels (`*.static` surfaces) plus 43 settings-page / banner widgets, with valid sizes and flags; after `/reload`, 0. The client loads an addon font file only when a **visible** FontString asks for it: with no window opened, 236 fonts were still refused after 60 s of retries; opening a window made all apply within ~15 s; with the probe shown, all applied on the first retry, 1 s after `PLAYER_ENTERING_WORLD`. Hence: a refusal is never recorded as applied, both registries are retried, and the probe stays up until nothing is pending.

Markers are **messages, not glyphs**: `missing` = `[未翻訳 / Not Translated]`, `stale` = `[要更新 / English Changed]` (`WFJ.MARKER`); on the quest window and the quest map the `stale` marker follows the Translator's live check when one is possible (ADR-019). The quest window shows them on a **banner**: a FontString created in `QuestFrame.init` by `Render.createBanner` on a small frame of ours parented to `QuestFrame` and raised ten frame levels above it (the panels are child frames whose background art would paint over a string on `QuestFrame` itself), in the stone band between the NPC name and the parchment (`TOP` y −52, 14 px bundled font, gold `WFJ.MARKER_COLOR`; the band holds nothing of the client's [verified: classic_era Vanilla/QuestFrame.xml:59–62, QuestFrameTemplates.xml:195–199]; on Forever's mainline QuestFrame (a `ButtonFrameTemplate`, told apart by its `TopTileStreaks` key) the parchment starts at y −62, so the banner takes the gossip banner's place instead, `TOP` x 20, y −36, 230 wide, centred in the strip between the title bar and the parchment) and shared by the three panels and the greeting prose (`questframe.greeting`) through `Render.setBanner`; `Render.updateBanner` recomputes it after every show / refresh / release / forget ("missing" before "stale", hidden when neither). With a banner the text widgets carry nothing extra: the English stays untouched in its own font. The gossip window has its own banner in its stone band (`Render.createBanner`), falling back to inline markers while the friendship bar is shown. `missing` is on by default; a record shown with `ctx.compact` never carries it: the quest list's titles, tracker headers and objective lines, the quest map details below the title (one marker per quest, on its title), and nothing else. An untranslated item's matched `Equip:` lines take the run, so the run gets no marker. A surface without a banner (the quest map details, tooltips) gets the message **inline** (`Render.inlineMarker`): on its own line above prose, before a single-line title, in `WFJ.MARKER_INLINE_COLOR`, and that widget takes the bundled font so the kanji render. Messages were chosen over glyphs after in-game passes: a grey dot suffix was invisible, inline orange unreadable, and inline red at body size too small.

### Whole-window rules (ADR-016)
- **Static labels before first show.** A window module shows its load-time labels (XML `text=`, OnLoad writes) at `init`, on `<surface>.static`, which is never released. The window's own tab `OnShow` → `PanelTemplates_TabResize` therefore measures the Japanese [verified: classic_era `Blizzard_FrameXML/Classic/CharacterFrameTemplates.xml:84–87`]. Modifier, area and master changes restore and re-apply them like every record.
- **Hook the leaf writer, not a `function=` handler.** `PaperDollFrame`, `PetPaperDollFrame`, `ReputationFrame`, `BankFrame` and `MerchantFrame` bind `OnShow` with `function=`, so the frame holds the function value and a global hook would not fire. Modules post-hook the globals those handlers call by name (`PaperDollFrame_SetLevel`, `MerchantFrame_UpdateMerchantInfo`, …), `hooksecurefunc(frame, method)` on a frame instance (`InboxFrame.Update`, `OpenAllMail.StartOpening`), or `HookScript` for an inline script.
- **No layout calls, no Blizzard field writes.** Addon code never calls `PanelTemplates_SetTab` / `UpdateTabs` / `SetDisabledTabState` / `TabResize`, `ShowUIPanel` / `HideUIPanel`, `:SetTextToFit`, `:UpdateButton` or `SpellBookFrame:Update`. It never assigns `.selectedTab` / `.bookType` / `.tooltipText` / `.UpdateTooltip`, never mentions `UIPanelWindows` or `Menu.ModifyMenu`, and calls `:SetScript(` only in `Main.lua` and `UI/Options.lua` (ADR-018, also `UI/OptionsWidgets`, `UI/KeyCapture`, `UI/RevealBinding`, `UI/AddonListButton`, `UI/Readings`, `UI/FixWindow` and `UI/MinimapButton`, on frames they create). `tests/python/test_forbidden_calls.py` enforces the list (comments ignored). A width measured once is kept: text toggled while a window is open, and buttons sized from English at their OnLoad, keep that width.
- **Scroll-box rows** (gossip quest rows, raid-info rows) follow `ScrollUtil.AddInitializedFrameCallback(scrollBox, cb, owner, true)`, Blizzard's own subscriber API. The callback accepts `(frame, elementData)` from the iterate-existing pass and `(owner, frame, elementData)` from later initializations.
- **Release.** Gossip, GossipChrome, Merchant, Bank, Skills, SpellBook and Trainer release their dynamic surface on the frame's `OnHide`: the skills pane on `SkillsFrame`'s, the bank on `BankFrame`'s, the spellbook on `PlayerSpellsFrame`'s and its `SpellBookFrame`'s; the quest map's surfaces release on their own frames'. Talents forgets `talents.tooltip` on the tooltip's `OnHide` and before each pass. Character, Reputation, PvPRank, Bags, Mail, Friends, Communities and Raid never release, because their writers run while the frame is hidden; Character releases only `character.title`, when the title is the player's name. A record whose widget the client rewrote without a hook is dropped by `Render.refresh`.

The `kind` a surface passes to `Render.show` → `Translator.resolve` → `lookup(kind, id)` is the lookup vocabulary: `quest.title` · `quest.objectives` · `quest.description` · `quest.progress` · `quest.completion` · `item.description` · `spell.description` · `spell.aura` (field-qualified: spell has two fields; `spell.aura` for aura tooltips) · `gossip` (keyed by fingerprint, ADR-005: the `id` is the gossip key from `Main`'s `gossipKey`: the first candidate key of the API English with a shipped row, else the full key; and `Lookup.get` delegates to `Lookup.keyed`) · `book` (ADR-022: the `id` from `Main`'s `keyOf("book")`, the same candidate-key pick over the type's rows; a book row is shipped under the hash of its English, since the client exposes no page id). The quest surfaces pass `"quest." .. field`; the tooltip and gossip surfaces use the same vocabulary. Objective lines (ADR-031) pass area `quests`, kind `objective` and the QuestObjective id found by fingerprint (`WFJ.ObjectiveIndex:match`), or, for a client template, kind `ui` with its key. Interface text passes area `ui`, kind `ui` and the UI key as `id`, with `ctx.args` from the index match. Client-name confidence: `[verified: classic_era FrameXML]` = read in `Gethe/wow-ui-source@classic_era`, `Interface/AddOns/Blizzard_UIPanels_Game/{Vanilla,Classic}/`; Forever parity for every name stays `[unverified: checklist 11]`. Load order: the quest UI exists when third-party addons load: `Blizzard_UIPanels_Game_Classic.toc` declares `## AllowLoad: game`, `## AllowLoadGameType: classic` and no `## LoadOnDemand`, and the predecessor reads `QuestInfoDescriptionText:GetFont()` at file top level on 1.15.5 [verified: `Blizzard_UIPanels_Game_Classic.toc:4–7`; `CQJT.lua:58`], so each surface's `init()` resolves its frames and installs its hooks at `ADDON_LOADED`, with no load-on-demand event to wait for. The exceptions are the load-on-demand addons, set up through `UI/LoadOnDemand`: `Blizzard_PlayerSpells` (spellbook and talents), `Blizzard_TrainerUI`, `Blizzard_RaidUI`, `Blizzard_GroupFinder_VanillaStyle` (the who list), `Blizzard_ObjectiveTracker` (the tracker), `Blizzard_Communities` (at login or on demand; an in-game check) and the addons in the last column of the Forever window table above.

## Data flow
client event → Blizzard writer writes English → our post-hook (`hooksecurefunc` on the writer, or `HookScript("OnShow")` when the writer is XML-bound) → surface reads English via API (id via API: `0` / `nil` forgets the surface; per field: show only when `en ~= ""` and `fs:GetText() == en`, else drop the stale record; tooltips: the `TextLeft<i>` widgets are the English, the description run becomes primary + companions) → `Collector.record` (gossip: `recordGossip`) with the API English, before the guard (→ `WFJ_Collector`) → `Render.show` → SurfaceState.capture → Translator.resolve (settings, modifier truth, lookup, runtime align, quest live check on `ctx.live`, player-token expansion) → SurfaceState.apply / restore (+ `UI/Readings.attach` / `detach`) → `modifier` / `enabled` / `area` / `markers` → `Render.refresh` open surfaces → frame `OnHide` → `Render.release`.
