# What spells a player can actually be shown on Forever

> **Superseded by [ADR-052](../adr/052-coverage-by-served-data.md) (coverage by served data).** Coverage and
> translation now take every spell the client serves; the artifact `pipeline/visible_spells.txt` and the tool
> `dev/visible_spells.py` were removed. Kept as the record of why the scope was tried and what it missed.

> 2026-09-18. Read from the installed clients: **Forever beta 1.60.1.69913** and **Classic Era
> 1.15.9.69722**, read-only, offline (ADR-021). Artifact: `pipeline/visible_spells.txt`, regenerated by
> `make visible-spells`.

## Why this exists

The re-pull leaves far more spell text with English and no Japanese than a player will ever read. Most rows
in `Spell.db2` are internal: procs, scripts, NPC-only abilities, test rows. Drafting all of them would spend
the translation budget on text nobody sees. The scope has to come from the client's own tables rather than
from judgement, or it is a guess ([principle 9](../architecture/principles.md)).

Measured on 2026-09-18 against `data/english/spell` and `data/spell`:

| spell field | lines with English and no Japanese | of those, player-visible | share |
|---|---|---|---|
| `description` | 19,797 | **7,085** | 35.8% |
| `aura` | 7,906 | **2,537** | 32.1% |
| `name` | 36,617 | n/a | not translation work at all: names stay English ([principle 2](../architecture/principles.md)) |

So the spell half of the re-translation is **9,622 lines**, not 27,703. The `name` column is listed only to head off the
arithmetic: it is the largest number on the page and none of it is work.

## The three sources

A spell is in scope when the client gives a reason its text reaches the screen.

| source | how it is reached | Forever | Classic Era |
|---|---|---|---|
| `item` | `ItemXItemEffect.ItemEffectID` → `ItemEffect.SpellID`: the spell whose description prints inside an item tooltip | 7,057 | 5,760 |
| `skill` | `SkillLineAbility.Spell`: a class or profession can learn it, so it is in the spellbook and at a trainer | 6,270 | 5,657 |
| `trait` | `TraitDefinition.SpellID`: a talent grants it | **523** | 9 |
| **union** | | **10,572** | 11,042 |

Every id is filtered to rows this build's `SpellName` actually holds, so a source pointing at a spell the
client no longer ships contributes nothing.

On Classic Era the item join is inline (`ItemEffect`'s own relationship map names the owning item), and the
tool falls back to it, which is why that build reports a sensible number too. That is the only
build-dependent branch in the derivation.

## `Talent.db2` is legacy on Forever: do not scope talents from it

This is the finding that matters, because `Talent.db2` (432 rows) looks like the obvious talent source.

- Its **layout hash is identical** on both builds and it holds the **same 432 rows**; every row differs from
  Classic Era's in exactly one field, which Forever zeroes. Nothing about it was updated.
- Only **517 of the 1,357** spell ids in its `SpellRank` arrays still exist in Forever's `SpellName`. A live
  table would not point at 840 spells the client does not ship.
- Forever's live talents are the **trait** tables, which Classic Era ships nearly empty:

  | table | Classic Era | Forever | layout hash |
  |---|---|---|---|
  | `TraitTree` | 1 | **17** | same |
  | `TraitNode` | 9 | **560** | same |
  | `TraitNodeEntry` | 9 | **656** | same |
  | `TraitDefinition` | 9 | **656** | same |
  | `TraitNodeXTraitNodeEntry` | 9 | **563** | same |
  | `ChrSpecialization` | 0 | **10** | same |

- **362 of the 517** legacy talent spell ids that still exist appear in `TraitDefinition`, so the trait trees
  are Vanilla's talents rebuilt plus new ones, not a parallel system.

Scoping talents from `Talent.db2` would therefore both **miss** Forever's new talent spells and **include**
ones that are gone. The generator uses `TraitDefinition` and says so in its own docstring.

## The two column maps, and their evidence

Neither table carries translatable text, so neither is in `io/client_tables.py`: they need no CSV, no source
stamp, no hotfix decode and no provenance, and building that machinery for them would be unneeded. Their maps are pinned in
`pipeline/wfj/dev/visible_spells.py` with the evidence below, and the tool **refuses a layout hash it was not
verified on** rather than reading a field on faith.

Both FileDataIDs were resolved from the **client's own root by name hash** (`DBFilesClient\SkillLineAbility.db2`
→ 1266278, `DBFilesClient\TraitDefinition.db2` → 4420327) on Classic Era, whose root carries name hashes; no
community listfile is involved (ADR-021 decision 2). Forever's root carries name hashes for only 144,963 of
its 1,441,771 FileDataIDs and none for `DBFilesClient\*`, so the id is the documented fallback there.

### `SkillLineAbility`: moved, verified by cross-build agreement

Forever **prepended two fields** (16 → 18, layout `0x0ED0E33F` → `0x224F7EA0`) and the row id moved from
inline field 0 to field 2, so every column shifted by two. Verified the way ADR-027 verifies a move, over the
6,047 ids both clients hold:

| Classic Era | Forever | agreement | next-best field |
|---|---|---|---|
| field 1 (`SkillLine`) | **field 3** | 6,047 / 6,047 = **100.0%** | 0.1% |
| field 2 (`Spell`) | **field 4** | 6,035 / 6,047 = **99.8%** | 0.0% |

The 12 disagreements are rows where Forever changed which spell the skill line grants: content, not the map.
A next-best of 0.0–0.1% is what rules out coincidence.

### `TraitDefinition`: same layout, newly populated

The layout hash is `0x060A9F4C` on **both** builds, so the field structure is the same by definition; what
changed is that Forever fills the table. Classic Era's 9 rows are too few to be a cross-build oracle, so the
column was established two other ways:

1. **Only one field holds spell ids.** Field 4: 647 of its 653 non-zero values are ids present in Forever's
   `SpellName`, 529 distinct. No other field is above 0%. (Beware the weak version of this test: a field of
   small numbers scores high simply because low spell ids exist; field 3's 656 distinct values, max 145,492,
   match nothing.)
2. **End to end, as `ItemXItemEffect` was verified.** `TraitDefinition` 133102 → spell 11210 → `SpellName`
   "Arcane Subtlety"; 133103 → 11222 "Arcane Focus"; 133104 → 11237 "Improved Channeling"; 133105 → 11069
   "Improved Fireball": Vanilla mage talents, with the matching `Spell.Description_lang` text. Classic Era's
   9 rows carry those same nine spell ids in the same field.

## The artifact

`pipeline/visible_spells.txt` is generated and committed, the way `pipeline/ui_inventory.txt` is, so cutting a
batch needs no game install. One line per spell, `<sources> <spell id>`, ascending, with the per-source counts
in the header. `test_visible_spells.py` checks the header's counts against the rows, so a regeneration that
half-wrote or mis-scoped the file fails the gate instead of silently shrinking the translation scope, and
checks that the set really is a small fraction of the untranslated backlog rather than a pass-through.

Regenerate after a client update:

```sh
make visible-spells WOW_DIR="<client folder>" PRODUCT=wow_classic_beta
```

## What this does not cover

- **Items have no equivalent filter and need none.** An item description is shown whenever the player sees
  the item, so the item half of the re-translation is its full 13,035-line gap.
- **A spell reachable only through a quest reward, a book or an NPC aura** is not in any of the three sources.
  The collector's recorded English is the cross-check for that: it proves a string was on screen, but its
  absence proves nothing, so it is never the filter.
- **Scope is not priority.** 10,572 visible spells is still more than one batch; which of them to draft first
  is a batching decision.
