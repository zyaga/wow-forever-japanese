# ADR-051: Coverage by served data

- **Status:** Accepted
- **Date:** 2026-10-02
- **Supersedes:** the visible-spell scope ([research, 2026-09-18](../research/2026-09-18-forever-visible-spell-scope.md)), which [ADR-027](027-column-maps-verified-per-build.md) described as a dev scope tool

## Context

Spell translation and spell coverage were scoped to "spells a player is likely to see": `pipeline/visible_spells.txt`,
generated by `make visible-spells` from three joins (a spell an item prints, a spell a class or profession learns,
a spell a talent grants). Coverage counted only those spells, and `translate_batch cut --visible` drafted only
those.

The list was a choice about what players see, not a fact the client states. It left out every spell no item,
skill line or talent names: world buffs, the auras creatures and bosses put on a player, and the descriptions of
those spells. On 1.60.1.70170 that is about 15,000 aura and description lines (7,319 distinct texts) that the
client serves and a player reads in a buff tooltip, while coverage read 99%. Nothing failed, because nothing
counted them.

The same blind spot applies to whole tables. The pipeline reads 31 DB2 tables through pinned column maps. A table
or column it does not read is invisible to coverage, and a new build can add one without anyone noticing.

## Decision

1. **Scope is what the client serves.** Coverage and translation scope come from the served-text inventory, not
   from a list of what a player is likely to see. The visible-spell filter is removed: `dev/visible_spells.py`,
   `pipeline/visible_spells.txt`, `make visible-spells` and `translate_batch cut --visible` are deleted. Coverage
   counts every served line of each surface.
2. **A served-text inventory per build.** `make served-columns` writes the committed `pipeline/served_columns.txt`:
   every text column of every DB2 table the install ships, the tables only the hotfix cache carries, the tables
   the reader cannot open, and the server caches (`Cache/WDB/enUS/*.wdb`). Text columns are found from the bytes,
   with no column map, so a table or column a new build adds is listed without a code change. Tables are named
   through the community listfile, because the archive root carries no names. Read-only, no network
   ([ADR-021](021-client-tables-from-the-local-archive.md)).
3. **Every served column has a stated disposition.** `pipeline/served_dispositions.txt`, written by hand, gives
   each column exactly one disposition from a closed set: `surface:<type>.<field>`, `surface:<type>.*` or
   `surface:ui:<Family>` (it ships in Japanese), `names`, `internal`, `no-display`, `covered-by:<column>`, `empty`.
   `internal`, `no-display` and `covered-by` need evidence; for `no-display` that is the Forever client's own UI
   source. A column with no disposition, a disposition for a column no longer served, a `covered-by` pointing at
   a column that is not a surface, and `empty` on a column with text all fail
   `tests/python/test_served_inventory.py`.
4. **No gap without a reason.** A served line of a surface that has neither shipped Japanese nor a stated reason
   (a names list, nothing to translate, English waiting on the Forever tables, an exclusion with its reason) is a
   gap. `tests/python/test_coverage.py` fails on any gap.
5. **The inventory moves with the build.** `make coverage` refuses when `served_columns.txt` is from another build
   than the Makefile's `forever_BUILD`, or when a served column has no disposition. Regenerating the inventory
   prints its delta against the committed file: the columns a patch added, dropped or changed. That delta is the
   per-build check of the harvest runbook.

## Consequences

- Coverage reports what is actually left. On 1.60.1.70170 spell tooltips and auras count 25,458 served lines
  instead of the visible subset; 10,369 ship Japanese and 15,064 are gaps (9,810 descriptions, 5,254 auras).
- A new table, a new column or a column that starts to carry text is caught at the next re-pull, as a line with no
  disposition, rather than found later by a player.
- The inventory doubles as an independent check on the pinned column maps: on 1.60.1.70170 the byte-level
  detection matches the maps of all 31 tables the pipeline reads (the only differences are declared string fields
  empty on every row).
- The community listfile is now an input of every re-pull. A stale listfile misses a table new on that build, so
  the runbook refreshes it with the one the UI extract uses.
- Dispositions are hand work: 171 tables with text gave 254 columns to decide. Columns that are shown in game and
  have no surface yet stay listed as not decided until a surface reads them or a reason is written.
- The translation work grows by about 15,000 spell lines, and the addon's spell data grows with them.
- One table (`collectablesourcevendorsparse`, a secondary-key layout) cannot be read yet; it is listed as
  `unreadable` and still needs a disposition.

## Alternatives considered

- **Keep the visible-spell scope and add sources (auras applied by creatures, world buffs).** Rejected: each new
  source is another guess about what a player sees, and the next blind spot fails silently the same way.
- **Translate every spell row with English, with no inventory.** Rejected: it fixes spells only. Tables and columns
  the pipeline does not read would still be invisible to coverage.
- **Pin a column map for every table the client ships.** Rejected: 1,161 tables, most without text, and every new
  build would need new pins before anything could be counted. Finding text from the bytes needs no map and is
  checked against the maps that exist.
