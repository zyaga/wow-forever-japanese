# ADR-015: UI text surfaces: targeted post-hooks over one dictionary, h1-gated live English, button fonts re-applied

- **Status:** Accepted. Implemented in `Core/UIStrings.lua` and `Core/UIStringKeys.lua` (the per-key tables), `UI/ButtonText.lua`, `UI/Labels.lua`, `UI/GameMenu.lua`, `UI/Tooltip.lua`, `UI/QuestFrame.lua`, `UI/QuestLog.lua`, `Core/Translator.lua` (`fill`), `Core/Const.lua`, `Core/Data.lua`, `Core/Settings.lua` (`area.interface`), `Main.lua`, `UI/Slash.lua`, `UI/Options.lua`. In-game verification is checklist 12.
- **Date:** 2026-09-14

## Context
ADR-014 gives the addon a dictionary of Blizzard interface words (`ui` rows: `{ text, h1, status }`, keyed by global-string name or `ItemSubClass:<c>:<s>`). The addon still ships no English (ADR-002), and it must keep the toggle contract: Japanese by default, hold the modifier for live English, a master switch and per-area switches, nothing added to the screen.

The research ([whole-UI text mechanism](../research/2026-09-14-whole-ui-text-mechanism.md)) compared overwriting global strings, a hook per frame, and a whole-UI widget-method hook. The goal is the whole UI except names, without per-screen work, so this builds on the mechanism already proven in-game (post-hooks on the client's own writers, ADR-009) over one dictionary. The whole-UI `SetText` metatable hook stays the documented alternative.

## Decision
1. **Targeted post-hooks per surface, one dictionary.** Each surface runs after the client's writer, reads the widget's current text, and hands dictionary hits to `Render.show(surface, recKey, fs, en, "ui", "ui", key, { args, refit })`. Records restore the live English on modifier hold, area off or master off, as for every other surface (ADR-009).
   - **Tooltips** (`UI/Tooltip.lua`): a structural walk of every line, left and right (`<Frame>TextLeft<i>` / `TextRight<i>`), records `ui.L<i>` / `ui.R<i>`. The name is never walked: the left line whose text is the item / spell name (`GetItem()` / `GetSpell()`), and left line 1, except on the four comparison tooltips (`ShoppingTooltip1/2`, `ItemRefShoppingTooltip1/2`), whose line 1 is the "Currently Equipped" header and whose name follows on line 2 (seen in-game). The right side of line 1 is walked (a spell's "Rank 1"). The description run (item) / description line (spell) of ADR-010 is excluded. An item with no description run still gets its structural lines. One forget at the start of a hover, one refit at the end.
   - **Quest frame panels** (`UI/QuestFrame.lua`): each panel's headers and buttons after its fields, on the panel's surface (records `ui.<widget>`). Detail: description / objectives headers, rewards header / choose / receive, learn label, required money, Accept, Decline; progress: required items / money, Continue, Goodbye; reward: rewards texts, Complete Quest, Cancel.
   - **Greeting panel:** `QuestFrameGreetingPanel` `OnShow`, surface `questframe.greeting`: Current Quests, Available Quests, Goodbye. The NPC greeting text `GreetingText` is translated as gossip on the same surface, hooked also through the by-name `QuestFrameGreetingPanel_OnShow` ([ADR-017](017-gossip-surface.md)).
   - **Quest log** (`UI/QuestLog.lua`): surface `questlog.labels`, its own surface so the detail pane's forget on a deselect does not drop them; shown on `QuestLogFrame` `OnShow` and after each `QuestLog_UpdateQuestDetails`, released on `OnHide`.
   - **Game menu** (`UI/GameMenu.lua`): `hooksecurefunc(GameMenuFrame, "InitButtons", …)`, surface `gamemenu`; the menu is rebuilt from a button pool on every show, so the surface is forgotten and every active pool button re-read (record `ui.<layoutIndex>`), plus the title plate `Header.Text` (`ui.header`; a fixed 256×64 background, so the title stays on the plate); released on `OnHide`.
   - `UI/Labels.lua` is the shared label step for the last three: a widget is shown only when its **whole** current text is a dictionary word or template (`index:match`, anchored, by English or by fingerprint below; "Suggested Players [3]" fills); a composite ("Learn Spell: (Complete)") is left alone, and a record from an earlier text on that key is dropped.
2. **`Core/UIStrings` index, built once at load** (`Main`, `WFJ.UIIndex`). Pure; `Main` injects the live English (`_G[key]`) and the hash.
   - A row is admitted only when `h32x2(normalize_v1(live English))` equals its shipped `h1`. Otherwise it is counted `mismatched` (hash differs) or `unresolved` (no live English) and the line stays English. Two admitted keys with the same live English and different Japanese are counted `ambiguous` and neither is indexed.
   - **Fingerprint rows.** Only an item subclass (a word the client exposes no global string for by design; `C_Item.GetItemSubClassInfo` returns the long name "Staves" where the tooltip shows "Staff") has no English to read, so `Main` returns none for `ItemSubClass:` keys and the row is matched by **fingerprint**: a live text whose hash equals the row's `h1` is that word (`index:exactKey`: by English first, then by hash). Only an `ItemSubClass:` row whose Japanese takes no argument qualifies; counted `hashed`. A global-string row whose string is missing on the client stays `unresolved` (a client drift `/wfj debug ui` must show), never fingerprinted. An `h1` shared by rows with different Japanese, or already answered by an English entry with other Japanese, is `ambiguous`.
   - A mismatch shows English **with no marker**. This is the `ui` form of `stale` (ADR-003): on a one-word label or button the stale marker would be the only thing on screen and would break the layout.
   - `index:match(text)` (used by tooltip lines and by `Labels`, so a template label such as "Suggested Players [%d]" fills too) → exact string, then templates (anchored patterns, the most literal text first, a longest-literal-word prefilter), then labels: a `"<entry>: "` prefix (`Reagents: Linen Cloth`), `"<entry>: <rest>"` (`Sell Price: …`), `"<entry> <number>"` (`Speed 2.60`).
   - **Typed captures.** A `%s` captures a **number** by default, so `"%s Armor"` never takes "Blackened Defias" from a set-piece line or a recipe's created item. `UIStrings.ARGS` declares the other argument kinds per key and index:
     - `word` (one word that must itself be a dictionary entry, such as a school or a standing, shown in Japanese; a line whose word is not an entry, e.g. "+3 Fire Spell Damage", is not that template) and `words` (a bag type, shown in Japanese when an entry, verbatim otherwise): the only kinds that may be shown in Japanese;
     - `text` (a name, a profession, a class list): verbatim, and never containing a period, so a prose sentence is never an argument;
     - `time` (a live duration): verbatim.
     `tests/python/test_ui_pipeline.py` fails when a text-capturing template is not declared. Label forms are whitelisted (`UIStrings.LABELS`: `SELL_PRICE` colon, `SPEED` / `RANK` number), so "Libram: Cleanse" is not read as `<Libram>: rest`.
   - `index:fill(ja, args)` puts the captured values into the Japanese (in order, or by `%N$`). A `word` argument that is itself an exact entry's English is shown as that entry's Japanese (school words, reputation standings, "Bag"); every other capture is shown verbatim, so a player named "Shadow" stays "Shadow", and numbers are never reformatted. Results are memoised per text. A Japanese template that asks for an argument the line did not have returns nil.
   - `Translator` takes `fill` as an optional dep: when `ctx.args` is present it runs before `expand`; nil or empty fails closed with reason `fill_failed`.
3. **Button text adapter** (`UI/ButtonText.lua`). A button is wrapped as the FontString-like object `SurfaceState` works on (text to the button, font to its text region), one adapter per button. Because a button's text region takes its Normal / Highlight / Disabled font object on a state change, the adapter re-applies the bundled font after `OnEnter` / `OnLeave` / `OnMouseDown` / `OnMouseUp` / `OnEnable` / `OnDisable` / `OnShow` while the bundled font is applied, and re-hooks `OnEnter` / `OnLeave` when a pooled button's owner re-sets them (the game menu). No `CreateFont` and no font-object edits: the addon creates and edits no font objects. If checklist 12 still shows missing glyphs on a button state, the fallback is addon-owned font objects, which would need that constraint revisited.
4. **One area.** `WFJ.AREAS` gains `ui`; the setting `area.interface` (default on, group `areas`) switches every `ui` record without a reload. `area.itemTooltips` / `area.spellTooltips` govern only the description text.
5. **StaticPopup is excluded.** `GameDialog` sizes its buttons from the text width right after `SetText`, so a post-hook swap would clip the Japanese. *(Superseded by [ADR-037](037-staticpopup-dialogs-and-owned-keys.md): on Forever the dialog lays out from its `dialogInfo` widths, not from the string (`gamedialog.lua:629–705`), and `UI/Popups.lua` writes the dialogs' text and buttons through widget methods only.)*
6. **Coverage comes from the client's source, not from in-game reports.** `python -m wfj.dev.ui_inventory <UI source> <GlobalStrings.csv>` writes `pipeline/ui_inventory.txt`: every global string each hooked window's XML / Lua references (quest frame, quest log, game menu, the Classic tooltip Lua) plus every GlobalStrings key in the tooltip families the C client prints (`ITEM_*`, `CHANCE_TO_*`, `*_COST*`, `SPELL_CAST/RECAST/RANGE…`, damage / armor / durability templates, …). `tests/python/test_ui_coverage.py` fails when an inventoried key is neither in `pipeline/ui_keys.txt` nor in `pipeline/ui_exclusions.txt` with a reason (retail-only system, name-carrying template, colour-coded, message not label, a widget no hook covers yet). In-game, `/wfj debug ui scan` (`UI/Scan.lua`, read-only) lists the English still showing on visible frames, marked `hook?` (the dictionary knows it: a widget is not hooked) or `key?` (not in the dictionary): a triage aid for a new window, not the discovery method.

## Consequences
- New coverage on an already-hooked surface is dictionary rows, not code. A new surface is one small module listing its widgets over `Labels` / `UIStrings`.
- **Stale records.** A widget the client rewrote without a surface hook firing (`ItemRefTooltip` reused for another link) is detected on the next refresh: `Render.refresh` drops any record whose widget no longer shows what we left there, instead of writing stale Japanese or English back.
- A client whose English differs from the English the Japanese was drafted against shows English on that line, silently. `/wfj debug ui` prints `shipped · indexed · hashed · mismatched · ambiguous · unresolved` and the first ten keys of each problem list, so a Forever client drift is one command away.
- Captured names (a faction in "Requires %s - %s", a reagent, a class list) stay English, as the name policy requires.
- The addon matches every non-description tooltip line against the index on each hover: an exact-table lookup, then the template list with a plain-find prefilter. `index:match` memoises results (hits and misses) per text, reset at 512 distinct texts, so a held or repeated hover costs a table lookup per line. Cost is not yet measured in-game (checklist 9 / 12).
- A fingerprint row is matched on the first 32 bits of the hash alone, so any tooltip line with that fingerprint is taken as that word; the rows are one- or two-word subclass names, where a collision with other text on the same tooltip is not expected, but it is not proven.
- Items to confirm in checklist 12 ([likely] until then): button state font switching (glyphs on hover / press / disabled), the game-menu layout after our write (fixed 144×21 buttons, `SetText` not `SetTextToFit`), and tooltip `TextRight` lines written from C (armor type, weapon speed).
- Screens without a hook stay English until a surface is added with the same inventory + coverage method ([ADR-016](016-whole-window-interface-coverage.md), [ADR-030](030-every-window-the-forever-client-loads.md)).

## Alternatives considered
- **Overwrite `_G` global strings at load**: taints secure readers (`ChatFrameUtil` reads `SLASH_*` inside `secureexecuterange`); misses XML-set text and the many tables that copy globals at file load; no live toggle. Rejected.
- **Whole-UI widget-method hook** (a `SetText` metatable post-hook plus a static-label pass): one mechanism for every screen, but fonts, per-call cost and taint are unproven on this client; it would need the in-game probe (P1–P5 in the research doc) first. Kept as the documented alternative.
- **A separate project per screen**: ruled out; here the per-surface code is small and shares one dictionary and one label step.
- **A stale marker on mismatched UI lines**: breaks one-word labels and buttons; English with no marker is the ADR-003 intent (never show text drafted against other English as current) without the layout cost.
- **Addon-owned font objects for buttons now**: the addon creates no font objects; revisit only if checklist 12 shows the adapter is not enough.
