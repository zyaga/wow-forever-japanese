# ADR-021: Client tables read from the installed client's local archive, not wago.tools

- **Status:** Accepted. Implemented in the reader `pipeline/wfj/io/blte.py`, `pipeline/wfj/io/casc.py`, `pipeline/wfj/io/db2.py`, `pipeline/wfj/io/client_tables.py`, the hotfix cache `pipeline/wfj/io/dbcache.py`, the CLIs `pipeline/wfj/dev/client_tables.py`, `pipeline/wfj/dev/tables_stamp.py` and `pipeline/wfj/dev/cut_db2_fixture.py`, `make tables-extract` in the `Makefile`, with tests `test_blte.py`, `test_casc_local.py`, `test_db2.py`, `test_client_tables.py`, `test_dbcache.py`, `test_client_tables_install.py` and fixtures `tests/fixtures/db2/`.
- **Date:** 2026-09-15

## Context
Every client table the pipeline reads (ItemSparse, SpellName, Spell, GlobalStrings, ItemSubClass, SpellItemEnchantment, QuestV2, ItemEffect) came from wago.tools CSV exports (`make wago-fetch`). wago may not list a new Forever build on the day it appears, and the beta-day harvest must not depend on wago.tools or any other external site. The tables have to come from the installed client itself.

The project's principles constrain how:
- **No pipeline dependency without an ADR**, stdlib first ([principle 1](../architecture/principles.md#1-blizzard-api-only), [ADR-004](004-zero-runtime-dependencies.md)).
- **No touching game folders**, except read-only exceptions. Reading `Cache/WDB/<locale>/*.wdb` is one ([ADR-020](020-quest-cache-harvest.md)). This ADR adds another: pipeline tooling may read the install's `.build.info`, `Data/**` and a client folder's `Cache/ADB/<locale>/DBCache.bin` (hotfixes), never write there, and the addon never reads them.
- **Duplicate ids are never resolved silently** ([principle 5](../architecture/principles.md#5-every-translation-is-keyed-by-the-game)).

The harvest is local pipeline tooling. The addon never reads the archive or anything derived from it at runtime.

## Decision
1. **A stdlib reader for the client's local archive.** `LocalArchive(wow_dir, product)` reads `.build.info` (the product row gives Build Key and Version), the build config under `Data/config`, the version-7 `.idx` files in `Data/data` (highest version per bucket), `data.NNN` entries (30-byte local header, reversed key checked; a blank header is handled by [ADR-026](026-blank-archive-header-is-unwritten.md)), the encoding file (`EN` v1, page lookup by content key) and the root (`TSFM` v2: locale-flagged blocks with FileDataID deltas, content keys and 64-bit name hashes). BLTE frames `N` (plain) and `Z` (zlib) are decoded, and each chunk is checked against its MD5, so a chunk read while the client rewrites it fails instead of passing with the right length. `E` (encrypted) frames come back as `EncryptedBlock` with the key name. An unknown mode, a size mismatch or a checksum mismatch raises `BlteError`. When `.build.info` lists a product more than once, the single `Active` row is used. Truncated or unreadable archive files raise `CascError` naming the archive, never a bare struct or file error. Game files are opened read-only. Stdlib only (`struct`, `zlib`, `csv`); no dependency is added.
2. **Tables are found by client path, through the root's name hash.** The name hash is Jenkins lookup3 `hashlittle2` of the upper-cased backslash path. No community listfile. Each table also records its 1.15.9.69722 FileDataID, used only when a root carries no name hash for the path (FileDataIDs are stable across builds). **Duplicate root entries:** when enUS root blocks give a FileDataID several content keys, the variants flagged LowViolence (`0x80`) or DoNotLoad (`0x100`) are set aside (wowdev.wiki TACT root content flags). If exactly one key is left it is used. Otherwise `CascError` lists every key with its locale and content flags. A key is never picked silently.
3. **A WDC5 reader that knows no column names.** `io/db2.py` covers:
   - dense tables: bit-level fields, storage types none / bitpacked / common data / pallet / pallet array / bitpacked signed, and shared string tables addressed relative to the field position;
   - sparse tables (flag `0x1`; ItemSparse and Spell are sparse): inline NUL-terminated strings, records padded to 4 bytes, ids from the offset map;
   - id lists, copy tables and relationship maps, which may be partial (ItemSubClass maps 71 of 72).

   Copies resolve after every section is read (a source may sit in a later section); a self-copy is ignored. A duplicate id raises. Secondary-key tables (flag `0x2`) are not implemented and raise. Anything else unexpected, including a struct or index error from a truncated block, raises `Db2Error` naming the table.
4. **Column names live in one place, pinned per table.** `io/client_tables.py` maps DB2 fields to wago.tools column names for the eight tables. Each table is pinned to its layout hash and field count, and both are checked from the header before any row is decoded. A different layout hash stops that table with `layout hash X, column map verified on Y: layout changed on this build, column map needs re-verifying` ([ADR-027](027-column-maps-verified-per-build.md)). A sparse table declares every string field, written or not, so string offsets can't drift. A record the relationship map leaves out gets parent 0, as wago.tools writes it, and the run prints how many.
5. **Number columns are signed by their declared type.** The DB2 field structure gives 0 bits for packed fields, so a field's declared size and sign cannot come from the file. `client_tables.Table.record` pins each field's declared type (`i8` / `u8` / `i16` / `u16` / `i32` / `u32` / `str`) for ItemSubClass, QuestV2 and ItemEffect, taken from WoWDBDefs' definition at the pinned layout hash, with a non-inline relation last (ItemEffect's `ParentItemID`). An archive value is cut to its declared size and signed if the type is signed. A number column in a table that declares no field types is refused (`… is a number column but the table declares no field types`), because its sign would be a guess. The types are copied into the column map at the pinned layout hash and never fetched at run time, so a layout change still stops the table (decision 4).
6. **Encrypted sections are skipped and counted, never read as zeros.** `read_file` zero-fills encrypted frames and returns their (start, end, key) ranges. The DB2 reader skips a section that overlaps one, or that has a TACT key and is already zero-filled in the file. A copied row whose source sits in a skipped section is counted as hidden. Encrypted bytes inside the header blocks (pallet, common data) stop the table, since every row would decode wrong. No keys are fetched from anywhere.
7. **Output is wago's CSV shape.** Line breaks are written as the two characters `\n` and read back as a break, so a literal backslash-n in text reads back as a break too (lossy, the same as wago.tools' export). A carriage return stays inside the quoted cell. The existing `io/wago.py` readers and the importers read the files unchanged.
8. **All or nothing, never into the game folder.** The CLI writes the selected tables to a temp folder and moves them into `--out` only when every one succeeded, so a failed run never leaves one build's CSVs beside another's. An `--out` inside `--wow` is refused. The read-only guarantee is also tested at run time: every write-capable call is wrapped during a full extractor run.
9. **wago.tools stays an optional cross-check.** `python -m wfj.dev.client_tables --wow <World of Warcraft> --product wow_classic_era --out <dir> [--tables …] [--hotfixes DBCache.bin] [--against <wago CSV dir>]`. `compare()` compares parsed values, not CSV text; comparison keys are parsed like values (GlobalStrings `BaseTag` stripped, ItemSubClass ids as ints), so two rows that collide after parsing raise `listed twice` instead of passing as two rows. `compare_readers()` also compares what the importers' own readers return. Rows that differ only where a hotfix applied are listed apart, not a failure: `--against` excuses a difference on a hotfixed row only where wago's value equals the archive's pre-hotfix value. It does not look at our value there, so it cannot catch a wrong hotfix decode when wago lacks the hotfix, and a hotfix that moves an ItemSubClass key shows as a difference.
10. **The hotfix cache is applied over the archive rows.** `io/dbcache.py` reads `DBCache.bin` version 9 (a 44-byte header, then entries naming the table hash, record id, push id and status); the entries of a record apply in (push id, file order) order and the last one decides: status 1 with data replaces the row, and any other entry (2 removed, 3 invalidated, 4 not public, or status 1 without data) removes it. This follows the community wowdev/DBCD hotfix reader (`HotfixReader.cs`, `DefaultProcessor`); the client's own ordering is not proven (on the Forever cache checked, every multi-entry record sits in the file in push-id order, so the two rules agree). All eight tables take hotfixes:
    - the text-only tables (ItemSparse, SpellName, Spell, GlobalStrings, SpellItemEnchantment) read a hotfix as its leading strings;
    - ItemSubClass, QuestV2 and ItemEffect are read by their declared field types (`dbcache.decode_fields`), following DBCD's hotfix reader (`DBCD.IO/Readers/HTFXReader.cs`, `HTFXRow.GetFields`): the fields in definition order at their declared sizes, a non-inline id left out (the entry's record id is the id), a non-inline relation read from the data like any field. A build whose table has no relationship map has no relation in its hotfix record either, so that layout declares its own record (Forever's ItemEffect: nine fields, `ParentItemID` 0 for a hotfix row, as for its archive rows). The record must be used up exactly, or be zero-padded only up to the next 4-byte boundary (as a sparse DB2 record is). Anything else stops the table, naming the table and row, instead of writing shifted values. That fit rule is the only guard on the decode.

    A cache of another build than the archive is refused, a folder given as the cache is refused, and a missing file means no hotfixes (the path is printed). `make tables-extract WOW_DIR=<client folder> [PRODUCT=wow_classic_era] [HOTFIXES=]` runs the CLI with that product, the cache at `Cache/ADB/enUS/DBCache.bin` and `--out` = the client's inputs folder. It reads nothing in the client folder beyond `.build.info`, `Data/**` and the hotfix cache: the product is a parameter, and a wrong one fails listing the install's products. If a hotfix decode stops the target, `HOTFIXES=` (empty) writes the tables from the archive rows only, pre-hotfix; re-extract with hotfixes once the cache matches the build.
11. **One source family for the imports.** The client-table imports (`wago-ids`, `client-text`, `wago-ui`) take `--src wago|db2`: `db2@<build>` labels tables read from an installed client, `wago@<build>` wago.tools CSVs. The two labels merge as one source, per field, so a re-import under either replaces the other's lines of the same fields. Each client carries its own label in the `Makefile` (`classic-era_SRC := wago`, `forever_SRC := db2`; [ADR-020](020-quest-cache-harvest.md) §12).
12. **Source stamp.** `make wago-fetch` and `make tables-extract` write `tables-source.txt` in the client's inputs folder once every CSV is in place, one line per table: `<table> <src>@<build>`. Before moving the new CSVs in, each target clears the stamp lines of the tables it fetches, and writes the new stamp only after the move. A run that fails before the move keeps the old CSVs and their stamp; a run cut off after the clear leaves those tables unstamped (refused), never under the old source's stamp. Other tables' lines are kept, so a `make wago-fetch` after `make tables-extract` restamps only the tables it fetched. A table is the CSV file name up to the first dot (`ItemSparse.csv`, `ItemSparse.excerpt.csv`). The preflight of `make import` / `make import-english` runs `python -m wfj.dev.tables_stamp check` for every client, with that client's pinned source and build, over every client-table CSV the imports read, so a missing or other stamp stops the target before any import step writes. `wago-ids`, `client-text` and `wago-ui` also check, and refuse, writing nothing, when a CSV has no stamp or a stamp other than their `--src` / `--build`. The label written into every English line therefore always names where the text came from. A malformed stamp line or a table stamped twice raises. `tables_stamp` has three subcommands: `write --dir D --src wago|db2 --build B TABLES…`, `clear --dir D TABLES…` and `check --src S --build B CSV…`. pfQuest, VMaNGOS and the quest-cache import's `--questv2` are not checked.
13. **Item tooltip English joins only the trigger types the tooltip prints.** The ItemEffect CSV carries `TriggerType` (DB2 field 1, per WoWDBDefs). `import english client-text` joins an effect's spell description into item `description` only for types 0 (Use), 1 (Equip), 2 (Chance on hit) and 5 (Use, no delay), `TOOLTIP_TRIGGERS`. Types 6 (learn spell) and 7 (loot tracker) are counted and printed (`item effects not in the tooltip, not joined: type 6: N, …`), not joined. On 1.15.9.69722 types 6 and 7 occur only on Season of Discovery rune items and `[DNT]` trackers; leaving them out is a judgement, not an in-game check, since those items can't be obtained on Era. Hidden types are skipped before the missing-spell check, so they never make an item incomplete (an item is left without description English only when a shown effect, 0/1/2/5, names a spell the Spell table lacks).

## Consequences
- **Extraction needs only the installed client.** On Classic Era 1.15.9.69722 the whole extraction takes about 1 s. Every table below has the same id set as wago.tools' CSV of the same build and 0 rows differing on the written columns, with hotfixes applied:

  | Table | Rows |
  |---|---|
  | ItemSparse | 24,442 |
  | SpellName | 31,249 |
  | Spell | 31,249 |
  | GlobalStrings | 19,624 |
  | ItemSubClass | 72 |
  | SpellItemEnchantment | 2,158 |
  | QuestV2 | 4,807 |
  | ItemEffect | 16,965 |

  The importers' own readers (ItemSparse / SpellName names, GlobalStrings, ItemSubClass) return identical results for both files. This build has no encrypted sections, and its encoding file, root and all eight tables use only BLTE modes `N` and `Z`.
- **Hotfixes carry real content on Forever.** Applied over the Forever archive, the hotfix cache replaces and adds ItemSparse rows (items such as 720 Brawler Gloves that the archive lacks) and replaces GlobalStrings texts (`SHARD_TRANSFER_*`). Tables extracted pre-hotfix miss those rows. ItemSubClass and QuestV2 have had no hotfix in any cache seen, so their declared types are still unchecked against a real hotfix.
- **A running client does not break the archive read.** Full extractions with the client running read every archive row identically. A patch in progress remains the unverified cause of truncated / checksum / content-key errors.
- **A layout change on Forever stops that table.** Its column map must be re-verified before it is extracted again. The quest-cache path is unaffected. Items, spells and UI text stay at the pinned build in the meantime.
- **Rows in encrypted (unreleased) sections are absent.** Nothing in them can show in-game before release, so no translation is lost.
- **Offline English sees rewording, not balance changes.** Spell description English is a template: numbers live in the spell-effect table. If Forever changes Tough Jerky from 61 to 80 health, `Restores $o1 health over $d` is unchanged and nothing offline flags it. ADR-007's in-game number check still catches it when the tooltip shows.
- **Item / spell tooltip lines are checked against their own tooltip English and can go stale.** `client-text` stores the tooltip and buff text, and `check` takes an item / spell `description` line's hash from it instead of the name. A baseline taken from the name (`english.of: name`) never makes a line stale: a rename re-baselines it, and the line's own tooltip English, when it arrives, is judged fresh. Changed tooltip English makes the line `stale` (sticky), and the addon still gates it: Japanese with the stale marker when names and numbers still match the live tooltip, English when they don't ([ADR-007 addendum](007-unaligned-ships-with-runtime-gate.md)). Numbers are checked only in-game.
- **Tests run without a game.** `casc_fixture.py` builds a minimal synthetic archive. `db2_fixture.py` writes synthetic WDC5 for the sparse, encrypted, pallet-array and malformed cases, and `test_dbcache.py` writes synthetic hotfix caches. `tests/fixtures/db2/` holds two small real tables (ItemSubClass 3 KB, QuestV2 34 KB) with wago's CSVs beside them, cut by `cut_db2_fixture.py`. `test_client_tables_install.py` runs only with `WFJ_WOW_DIR` and `WFJ_WAGO_DIR` set (its hotfix check also needs `WFJ_HOTFIXES`); CI skips it.
- **An inputs folder with no source stamp** stops the next `make import` / `make data` in the preflight until one `make wago-fetch` or `make tables-extract` rewrites the CSVs and their stamp.
- **More format surface to own.** A new archive version, DB2 version or BLTE mode on Forever raises rather than guessing. Supporting it is a code change.

## Alternatives considered
- **wago.tools only**: the dependency this ADR removes. wago may not list a new Forever build on the day.
- **A third-party CASC / DB2 library or tool** (CascLib, TACTSharp, DBCD, …): a pipeline dependency that needs its own ADR, and often not Python. It would still need our column map. The subset of the format we read is small.
- **Pinned FileDataIDs from a community listfile**: unnecessary, because the root carries name hashes. It would also add an external source.
- **Column names from WoWDBDefs definitions at run time**: an external source on beta day. Pinning the few columns we read is enough, and it fails loudly when a layout changes. The declared types of three tables come from WoWDBDefs the same way: copied at the pinned layout hash, never read at run time.
