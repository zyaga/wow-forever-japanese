# ADR-009: Surfaces post-hook the client's writer functions and refuse widgets that do not show the API English

- **Status:** Proposed; accepted once in-game checklist 1–2 pass.
- **Date:** 2026-09-13

## Context
A surface must write Japanese *after* the client has written English into a FontString, and must read that English from the API, not the widget (ADR-002; the render mechanism in [Addon Modules](../architecture/addon-modules.md)). The predecessor registered the quest events (`QUEST_DETAIL` …) and hooked `SelectQuestLogEntry`, then deferred 0.1 s, because at those points the client had not yet written the text. Event dispatch order between addon frames and Blizzard's is not a contract, and `SelectQuestLogEntry` runs *before* `QuestLog_UpdateQuestDetails` in the same call chain. On that evidence, "capture may need one deferred tick" was part of the early surface contract.

Reading the Classic Era FrameXML (`Blizzard_UIPanels_Game/{Vanilla,Classic}/`) shows every quest write happens inside a small number of global functions: `QuestInfo_Display` (detail / reward panels), `QuestFrameProgressPanel_OnShow` (progress panel), `QuestLog_UpdateQuestDetails` (log detail pane). The first and last are called by name from Lua, so `hooksecurefunc` on the global (which runs the hook strictly after the original returns) catches every call. The progress writer is different: the XML binds it as `<OnShow function="QuestFrameProgressPanel_OnShow"/>` (`Vanilla/QuestFrame.xml:267`) and the client reaches it only through `panel:Hide(); panel:Show()` (`Classic/QuestFrame.lua:81–82`), so `[likely]` the frame holds the function *value* and a hook on the global would not run. This is unverified in-game (the stub models it; checklist 1 observes it). `HookScript` on the frame is correct under either binding semantics, so nothing hinges on the premise. `hooksecurefunc` itself is in live use by the predecessor on 1.15.5 (`CQJT.lua:651`, on `SelectQuestLogEntry`). Hooking once at `ADDON_LOADED` is sound because the quest UI is already loaded: `Blizzard_UIPanels_Game_Classic.toc` declares `## AllowLoad: game` / `## AllowLoadGameType: classic` and no `## LoadOnDemand` (`:4–7`), and the predecessor reads `QuestInfoDescriptionText:GetFont()` at file top level (`CQJT.lua:58`).

## Decision
- **Hook the writer, not the event.** A surface installs `hooksecurefunc` post-hooks on the client function(s) that write the text it translates, resolved by name through `Compat` (an unresolved name is a `/wfj debug` line, never an error). Events are used only where no writer function exists (gossip's ScrollBox initializer, tooltips' `OnTooltipSet*` scripts; those are already post-write callbacks).
- **Frame-script exception.** A writer bound in XML by `function=` is hooked on the frame (`panel:HookScript("OnShow", …)`), not on the global, because `[likely]` the frame holds the function value and `hooksecurefunc` on the name would not fire (`QuestFrameProgressPanel` is the quest case); `HookScript` is correct under either semantics. `HookScript` runs after the original script the same way `hooksecurefunc` runs after the original function.
- **English from the API, written to the widget only if the widget agrees.** For each field the surface reads the API getter and the target FontString; the field is shown only when the widget resolves, the English is non-nil and non-empty, and `fs:GetText() == en`. Otherwise the element is left untouched and no record is made. This catches client-side decoration (the localised `FAILED` string, `" - (Failed)"` in enUS, on a failed quest's log title), an empty field, a future FrameXML change that moves text to another widget, and any ordering surprise. The safe failure is always "frame untouched" ([principle 3](../architecture/principles.md#3-japanese-by-default-english-one-key-away)).
- **A skipped field drops its stale record.** A record from an earlier quest on a widget we now skip is forgotten with `SurfaceState.drop`, which puts the client's English back **only** if our applied text is still on the widget and otherwise resets only the font. Our old Japanese is never restored over text the client has since written. An id of `0` / `nil`, or a quest-window panel giving way to another, forgets the surface whole (`Render.forget` = `dropAll`). `release` on `OnHide` stays the restore-everything path; `drop` is for a widget that may have been rewritten while the frame stayed open.
- **Release on the frame's `OnHide`.** It is the superset of every close path (`QUEST_FINISHED → HideUIPanel → OnHide`, Esc, accept, decline, the log's close button).
- **No deferred tick for quests.** The contract sentence in `addon-modules.md` becomes the *fallback* rule for a surface whose writer cannot be hooked.

## Consequences
- Deterministic ordering: our write always follows the client's, so no `C_Timer`, no ticker, no race with `QuestInfo_Display`'s own `SetText`; the busted stub can replay the exact write sequence and prove the surface synchronously.
- Coupling to FrameXML function names rather than to events. Mitigated by `Compat` (named degradation) and by the equality guard (a renamed widget cannot be written to by accident). Forever parity is checklist 11 in [Testing Strategy](../testing/strategy.md).
- The guard can suppress a legitimate translation when a client decorates a widget we did not anticipate, visible as "no Japanese here", never as wrong text.
- A field skipped by the guard drops its stale record instead of leaving it, so a later modifier press / release cannot resurrect an earlier quest's Japanese on a widget the client has rewritten. The quest window carries one surface per panel (`questframe.detail` / `.progress` / `.reward`) so a panel switch can forget the hidden panel without touching the visible one.
- `hooksecurefunc` is the sanctioned hook (in live use by the predecessor on 1.15.5, `CQJT.lua:651`), and there is no taint path on these unprotected frames: `QuestFrame.xml` / `QuestLogFrame.xml` declare no `protected="true"`. A frame whose writer is XML-bound costs one `HookScript` instead; the coupling is to the frame name rather than the function name, still mitigated by `Compat`.

## Alternatives considered
- **Register `QUEST_DETAIL/PROGRESS/COMPLETE` + `QUEST_LOG_UPDATE` and write in our handler**: dispatch order relative to Blizzard's handler is undocumented; when ours runs first the client overwrites us with English. Rejected.
- **Event + `C_Timer.After(0, …)` (the predecessor's shape)**: works, but adds a tick, a timer dependency, a one-frame English flash, and an unverifiable window in tests. Kept as the documented fallback only.
- **`hooksecurefunc("QuestFrameProgressPanel_OnShow", …)`**: the obvious symmetric hook. Under the `[likely]` binding semantics it would not fire, because the frame script would hold the function value bound by the XML, not the name. `HookScript("OnShow")` on the panel is correct either way.
- **Leave a skipped field's record in place**: a later Alt press / release would then restore an earlier quest's Japanese over the client's new text. `drop` prevents that.
- **Re-run `QuestInfo_Display` as the refit**: rewrites English, re-enters our hook: a loop. `UpdateScrollChildRect()` (what Blizzard calls at the end of the log update) is the refit instead.
- **Trust the API English without the widget check**: simpler, but a decorated widget (the `FAILED`-suffixed title) would be restored to the undecorated string, violating "put back exactly what the client wrote".
