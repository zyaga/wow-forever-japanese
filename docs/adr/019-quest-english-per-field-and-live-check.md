# ADR-019: Quest progress / completion English from VMaNGOS, a per-field English hash, and a live check for the stale marker

- **Status:** Accepted. Implemented in `pipeline/wfj/io/vmangos.py`, `pipeline/wfj/cmd/import_.py` (`import english vmangos`), `pipeline/wfj/core/status.py` (`Scope.srcs`), `pipeline/wfj/cmd/check.py` (`english_ref`, `fallback_baseline`, `OWN_ENGLISH_LATER`, `english.of`), `pipeline/wfj/emit/lua_writer.py` (no `h1` for a fallback-hash quest field), `pipeline/wfj/core/report.py` (`stale_rows`, gossip header), `pipeline/wfj/cmd/stats.py` (`--stale`, `--dump`), `pipeline/wfj/dev/gen_attribution.py` (VMaNGOS attribution), `Makefile` (`VMANGOS_DB`, `VMANGOS_SHA`), `addon/WoWForeverJapanese/Core/Collector.lua` (`fingerprints`, `MEMO_MAX`), `Core/Translator.lua` (the `fingerprints` dep and the live rule), `Main.lua`, `UI/QuestFrame.lua`, `UI/QuestLog.lua`, `UI/Render.lua` (`ctx.live`). In-game verification is checklist 15.
- **Date:** 2026-09-14
- **Amended by:** [ADR-053](053-forever-shown-english-is-the-english.md): `check` consults collector English for quest and gossip, the collector import replaces a pfQuest or VMaNGOS line for the same (id, field), and a collector line outranks VMaNGOS on a later import.

## Context
Quest progress and turn-in (completion) text, NPC gossip and book text are **server-only**. No client API returns them by id, no DB2 table holds them, and the client cache does not either: a quest-ID scan of `questcache.wdb` (Classic Era 1.15.9.69722) found title, objectives and description only. They cannot be pre-verified on the Forever beta.

pfQuest supplies only title / objectives / description English. Without an English of their own, completion lines borrow the **description** hash as their English baseline, and the numbers and completeness checks cannot run on them. A completion translation with a wrong count or a first-paragraph cut would ship `trusted`, and a change to the real completion English would be invisible.

The addon also needs a **live English check for quests**. Without one, a `trusted` quest line is applied whatever English the client shows, and `stale` is decided only at build time (ADR-003).

## Decision
1. **VMaNGOS is the English source for quest progress / completion and gossip.** The VMaNGOS world database, as its SQLite snapshot (`vmangos/core` release `db_latest`, asset `db-sqlite-13b49dc.zip`, read with stdlib `sqlite3`), is imported by `wfj import english vmangos`:
   - quest: per `entry`, the row with the highest `patch`; `RequestItemsText` → `progress`, `OfferRewardText` → `completion`; `src vmangos@13b49dc`;
   - gossip: `broadcast_text.male_text` / `female_text` referenced by `npc_text.BroadcastTextID0..7`, `gossip_menu_option.option_text`, `quest_greeting.content_default`; `id = hash = key(normalize_v1(en))`, no `npcs`.

   Measured match with Blizzard's cached 1.15.9 text, over the quests of that `questcache.wdb` scan: VMaNGOS `Details` 473 / 476, `Objectives` 471 / 475 (pfQuest 470 / 475 and 471 / 474). Title / objectives / description stay pfQuest's, except where Blizzard's own cached text replaces them ([ADR-020](020-quest-cache-harvest.md)).
2. **The English hash is per field, with a per-field source.** `check` records `{hash, src}` of the field actually used: own field → description → name → joined scope. Progress / completion use their own VMaNGOS English when it exists, and numbers and completeness run on them. The joined-scope fallback excludes progress / completion, so a title-only pfQuest quest keeps its hash; a quest with no title / objectives / description English at all (only VMaNGOS progress / completion) has nothing to join, so its title / objectives / description lines are `rejected no_english_id`. **A quest line checked against another field's English** records which one, `english = {hash, src, of}` with `of` ∈ `description` · `joined`, and `generate` ships **no `h1`** for that field. The live check (3) and the collector's known check then never compare a field's live English with another field's hash: the live check does not run and the build-time status decides, and the collector records that English. Without this, such lines would show the stale banner on every view. **Re-baseline, once:** a progress / completion line whose prior `english.src` starts with `pfquest@` was checked against the description's hash, so it is judged fresh against its own English rather than `stale`. After that, a VMaNGOS change marks the field stale like any other.
3. **The stale marker follows a live check on quest surfaces.** The quest windows and the quest log pass the API English as `ctx.live`. The Translator asks `Collector.fingerprints(live, player)` for the `h1` of each ADR-017 candidate (full, name only, nothing replaced) and compares them with the field's shipped `h1`:
   - **no fingerprint equal** → the Japanese shows **with** the stale marker;
   - **one equal** → no marker, even on a build-time `stale` line;
   - **no fingerprints** (the player's name, class or race not known yet) → the build-time status decides.

   The mismatch case shows Japanese because a Japanese player is better served by Japanese marked as possibly stale than by English: they can hold the key for English. ADR-003 stands: stale ships, and there is no runtime names / numbers gate for quests.
4. **An offline fix list.** `wfj stats --stale PATH [--dump SAVEDVARIABLES]…` writes every shipped quest line that is `stale`, or whose English differs across sources, as JSONL with the Japanese and both English texts (one `others` entry per source and hash). `check` does not consult collector English (ADR-013), but the report reads it. Collector English stored in `data/english/` is read directly. `--dump` also reads a collector dump's quest entries, and it is the only way to see Blizzard's text disagree with a curated source: `import english collector` keeps a pfQuest / VMaNGOS line and stores nothing for that (id, field) (it only prints `differs`), and the VMaNGOS import replaces collector lines for the fields it provides. Mismatches are fixed there, without meeting them in-game.
5. **Books and trainer greetings** are their own surfaces ([ADR-022](022-book-and-trainer-greeting-surfaces.md)): `page_text` is imported as type `book` and `npc_trainer_greeting` as `trainer_greeting`.

## Consequences
- Numbers and completeness run against the real completion English, so fewer completion lines pass than when they borrowed the description hash. The Japanese lines that stop shipping show live English instead. Names and numbers are checked against the whole quest scope, so a title, objectives or description line whose name or number appears only in the progress / completion English can now pass.
- A hand-written correction that covers one paragraph of a two-paragraph reward text is rejected by the completeness rule; `test_data_integrity.py` records such exceptions (`TRUNCATED_BY_OWN_ENGLISH`).
- **False stale markers are possible.** The Japanese still shows in every case; `stats --stale --dump <file>` finds these lines from a play session's collector dump.
  - **Source text differs from Blizzard's.** VMaNGOS progress / completion differ for roughly 1% of quests, and so do pfQuest title / objectives / description, so a correct translation shows the marker there.
  - **`$G` gender text.** Text resolved for a female character from a `$G` branch never matches the first-branch hash. Such fields ship `h1f`, the female variant's `h1`, and a fingerprint equal to it matches, so no marker shows ([ADR-024](024-gender-variants-and-short-name-candidates.md)).
  - **Literal class / race words.** A text with a `$C` / `$R` token and also the same class or race word written literally normalizes differently for players of that class or race, so it is marked for them.
  - **A player name that is also a word in the text** ("Light") is replaced there too, so no candidate matches and the line is marked.
  - **Short names.** A player name under 3 code points is never replaced by `normalize_v1`; short names are compared through short-name candidates ([ADR-024](024-gender-variants-and-short-name-candidates.md)). A match removes the marker, no match lets the status decide.
- **Shared Collector function.** The live check reuses the Collector's candidate text path (`Collector.fingerprints` beside `Collector.keys`), so the quest hash and the gossip key cannot drift apart. The quest window re-resolves its records on every refresh (about 50 resolves per detail open), so fingerprints are memoized per player and text, and the memo is dropped at `Collector.MEMO_MAX` = 64 entries.
- **The collector's known check covers progress / completion** with their VMaNGOS English. A field shipped with no `h1` (its English is another field's) is never known, so its live English is recorded.
- `Data/Meta.lua` carries `vmangos = "13b49dc"`. The VMaNGOS gossip import refuses to replace existing `vmangos@` lines with zero lines, keeps `npcs` a collector dump added to a VMaNGOS line, and treats two different texts under one hash as an error ([principle 5](../architecture/principles.md#5-every-translation-is-keyed-by-the-game)). `ATTRIBUTION.md` credits the VMaNGOS database (GPL-2.0). The `stats` gossip header reads `gossip: N keys with English · M translated`.
- **A moving input.** `db_latest` moves: a new snapshot sha needs `VMANGOS_SHA` bumped in the same PR as the regenerated data.

## Alternatives considered
- **Live English on mismatch, no Japanese (fail closed)**: rejected. A Japanese player is better served by Japanese marked as possibly stale than by English.
- **A runtime names / numbers gate for quests** (as ADR-007 does for items / spells): rejected. It adds complexity on every quest window, and the offline report is how mismatches get fixed.
- **Keep the description-hash fallback for progress / completion**: rejected. Completion changes would stay invisible, and numbers / completeness would never run on those lines.
- **CMaNGOS / TrinityCore world data**: not needed. VMaNGOS matches Blizzard's cached text on at least 99% of the measured quests, and it is a Vanilla (1.12) database.
