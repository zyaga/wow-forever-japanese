# ADR-012: Human decisions survive regeneration: carry corrections and rulings across `make data`, rank a correction first

- **Status:** Accepted
- **Date:** 2026-09-14

## Context
Quest 456 showed English under the `[未翻訳 / Not Translated]` banner. Its complete 2009 translation (Az, `qjp@0.5.8`, three paragraphs) is in `data/`, rejected `alignment_failed:bore` for one misspelled mob name: `Thistle bore` for `Thistle Boar`. The fix is one word, but a fix typed into `data/` did not survive. `import predecessor` replaced the quest / item / spell stores wholesale from the predecessor files, so `make data` discarded every hand edit and every `ruling`. `provenance.class: correction` was a valid class, but nothing preserved it and nothing ranked it (an unlisted `correction@…` source ranked last).

Rebuilding is how pipeline fixes land: an importer normalisation change (paragraph breaks, placeholders, credit stripping) reaches every line only because the stores are rebuilt from the pinned inputs. A merge would keep the old stored text, and because `ja_identity` collapses whitespace, an old whitespace variant would match the new one and never be replaced.

A scan of the rejected quest variants whose only failures are near-miss names found 71 candidates (0.7 similarity): some real typos, some checker gaps.

## Decision
1. **Rebuild imported text; carry human decisions.** `import predecessor` still rebuilds the three stores from the pinned inputs. Before rebuilding it reads the existing stores and carries every variant whose `provenance.class` is `correction` and every variant with a `ruling` (`core/decisions.carried`, sorted canonically by id, field, corrections first, `reject` rulings last, source, text, so a rebuild is byte-stable whatever `check` promoted last). After rebuilding, `Collector.carry` applies three rules.
   - A **correction** is always kept as its own variant. Only a correction byte-identical (NFC) to one already there is **redundant** (counted, not duplicated). Whitespace and paragraph breaks are significant, because restoring `\n\n` is a real correction under ADR-011's completeness rule.
   - A **ruled imported variant** whose text (`ja_identity`) a rebuilt variant has → that variant takes the ruling; new text → appended to `conflicts` with its own `provenance`, `extra` and `ruling`.
   - An (id, field) the inputs no longer produce → the carried variant becomes the line, except a `reject`-ruled variant with nothing to be rejected against. That one is an orphaned reject: it is held (`Collector.orphans`), not shipped alone. Decisions are carried before the lineage sources merge, so a line only a lineage source produces does not exist yet at this carry; `run_predecessor` carries the orphans again after the lineage merge, before `carry_english`, and the ruling re-attaches to the lineage variant with the same text. One whose (id, field) still no input produces is counted as orphaned.

   It prints `carried human decisions (corrections / ruled variants / redundant corrections): quest N/N/N · item N/N/N · spell N/N/N`, plus `not carried: <type>: N orphaned rejects` when non-zero. The lineage sources (QuestJapanizer, CraftJapanizer_Quest) merge rather than rebuild: `make import` merges them inside the same `predecessor` pass, after this carry (the standalone `import questjapanizer` / `import craftjapanizer-quest` merge into the committed store the same way). A ruled lineage variant carried at the rebuild collapses with its re-import (origin appended once). No importer ever collapses into a **correction**: identical imported text becomes its own variant beside it, so a correction keeps its attribution and shape.

   There is no exclusion by translator. Exclusion by credit label cannot keep a translator's text out (identical text from another source survives under the community label, and co-credits survive), so a real removal request is handled on its own.
2. **A correction ranks first.** `status._rank` = (correction first, English paragraphs covered, source priority `cqjt` > `cjq` > `qjp` > `qjwiki`, named translator over community label). Only variants passing every rule are ranked: a failing correction never ships and never blocks a passing import. `tiebreak` is recorded when a correction wins by rank. Extends ADR-011 §4.
3. **The correction shape.** `{"class": "correction", "translator": <who wrote the Japanese>, "source": "correction@<YYYY-MM-DD>", "imported": <date>, "corrects": <source of the corrected variant>, "note": <what changed>}`, no `origins`. `validate_line` requires `translator` and `corrects` (`name@ref`) for a `correction`, on the line and on every `conflicts` entry; a correction waits in `conflicts` until `check` promotes it. For a name fix `translator` is the corrected variant's translator. The committed-data integrity test checks that each correction's (`corrects`, `translator`) names a variant on its line, so a misattributed correction cannot slip past the structural rule. A correction is written as an extra object in the line's `conflicts` (the line's own text can stay); `make check` promotes it. `paragraphs.first_paragraph_only` evaluates `corrects` when present, so a corrected text from the relabelled wiki layer (`cqjt` + `questjapanizer-wiki`) stays under ADR-011's structural truncation rule.
4. **Carry the English baseline too.** A line's `english` (`{hash, src}`) is the English its (id, field) was last checked against, the baseline `check` needs to derive `stale` (ADR-003). A rebuild would otherwise reset it to `null`. `run_predecessor` loads each store once and takes both the carried decisions and a map (id, field) → `english` for every non-null baseline. Given `--questjapanizer` / `--craftjapanizer-quest` (as `make import` passes them), one pass runs, in order: rebuild from the predecessor inputs → `Collector.carry` → merge QuestJapanizer → merge CraftJapanizer_Quest (`merge_lineage`) → `Collector.carry_english` → save once. `carry_english` deep-copies each baseline onto the rebuilt line with that (id, field). The baseline carry comes last because a baseline can only be put back on an (id, field) that exists, and some lines only a lineage source produces (quest 928 objectives, 1958 objectives / description, 4511 title / objectives / description / completion, 6261 completion). It is keyed by (id, field), never by text: `check` re-judges the Japanese on every run, so a rebuild that changes the Japanese keeps the baseline, matching `make import-english`, which never touches the Japanese. A rebuilt line with no prior baseline keeps `english: null`; a baseline whose (id, field) none of the given inputs (predecessor or lineage files) produce is counted, not written. It prints `carried english baselines: quest N · item N · spell N`, plus `english baselines not produced by the inputs: quest N · item N · spell N` when any were lost; on the pinned inputs that second line does not print.
5. **One stored order for `conflicts`.** The sorted carry above does not make a rebuild byte-stable on its own: `promote` builds a line's `conflicts` as [displaced variant] + the others, so the stored order would depend on which variant had been promoted before. `check` writes every line's `conflicts` in one canonical order after promotion (`core/dedupe.canonical_conflicts`): `provenance.class` `human` < `correction` < `machine` < any other class, then `source`, `translator`, `ja`. The order is total and independent of history. Winner selection never reads it; the winner is still chosen by rule, ruling and rank (§2).

## Consequences
- A `correction` or a `ruling` in `data/` survives `make data`; imported text is still rebuilt, so normalisation fixes keep landing. `make data` twice on the real inputs is byte-identical, and `make data` on a clean checkout is a fixed point: it reproduces the committed `conflicts` order whatever promotion history produced it.
- An edit to an imported line's `ja` that is **not** marked `correction` is still overwritten by the next `make data`. Nothing detects it.
- Two passing corrections on one line tie (same rank) and leave it `rejected/duplicate_conflict`: correct a correction by editing it, not by stacking a second. An `accept` ruling on another variant still wins over a correction (`resolve` reads accepts first); remove it when correcting.
- A `reject` ruling on every hand-written variant of a line lets a passing machine draft ship there: the hand-written text no longer bars it (ADR-014 §3), and `validate --base` accepts that hand-written → machine change ([ADR-023](023-server-only-text-drafted-in-measured-batches.md)). A reject is a person's decision on text they read, or ruled on as a set, and is carried like any other ruling. A `reject` is permanent: the ruled variant is never a candidate again, even alone on its line and even when later English or a rule change would make it pass. Reject rulings let a machine draft replace only text that shipped nothing at the `validate --base` ref; a shipping hand-written line needs an explicit `accept` on the machine line.
- A ruled imported variant is carried by text; if a later importer normalisation changes that text beyond whitespace, the ruled old form stays (with its ruling) beside the new form rather than following it.
- A committed correction must ship: the integrity test fails when a correction is not its line's shipping variant (for example after an English refresh rejects it), which surfaces it for a person.
- A ruled or corrected variant whose input text has since changed persists as its own visible variant in `conflicts`. It is not silently dropped, and not silently reconciled.
- Prior `english.hash` values survive `make data` too (Decision 4): a full `make data` and `make import-english` + `make check` derive identical statuses, so a changed English is `stale` through either path and stays `stale` across reruns until an audit re-verifies it (ADR-003).
- A near-miss name candidate from `dev/list_name_typos` is never a fix until a person reads it. Many are not typos: singular/plural checker gaps such as `Missionary` / `Missionaries`, zone names the English shortens such as `Tirisfal Glades`, NPCs or places the English never names, a typo in the English (`Quatermaster`).
- How a correction writes a name: a name is written exactly as the English sentence writes it, following the style guide, so a line whose Japanese used the full item or zone form (`Tirisfal Glades` where the English says `Tirisfal Glade`, `Linen Cloth` for `Linen`) is corrected to the English form and ships Japanese. An English typo in a name is copied as written (`Dirania Silveshine`, quest 3521), since the check and the Alt view compare against that English. In a title, a name is written exactly as the English title writes it (often an item's name, `Sharptalon's Claw`), not its full or translated form; a real name that was translated, written in katakana or dropped goes back in English letters (`Westfallシチュー` → `Westfall Stew`), and race and class words take the glossary katakana.
- Corrections are reviewed line by line against the English: each one names the corrected variant's translator and source and says what was fixed (a name spelled as the English has it, a count matched to the English, an added paragraph removed). Where no hand-written variant was worth keeping, the variants are ruled `reject` and a whole-line machine redraft replaces them ([ADR-023](023-server-only-text-drafted-in-measured-batches.md)). A ruling picks a variant; it does not override the rules, so an accepted variant that still fails a rule is decided again.

## Alternatives considered
- **Merge-always import** (seed the predecessor import from the store, like the lineage importers): rejected. Normalisation fixes stop landing (whitespace-collapsed identity keeps the old text), and a pin bump would leave old and new texts side by side as `duplicate_conflict` ties.
- **An overlay corrections file** applied after import: rejected. It is a second source of truth; `data/` already is the database (ADR-006), and a correction belongs next to the variant it fixes, with provenance.
- **A CI guard for unmarked hand edits**: not possible. The pinned inputs are not in CI, so CI cannot tell an imported text from an edited one.
