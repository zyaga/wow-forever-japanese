# ADR-020: Blizzard's cached quest text outranks pfQuest

- **Status:** Accepted. Implemented in `pipeline/wfj/io/wdb.py` (`read_quests`, `read_ids`, `decode_payload`, `WdbError`, `PLACEHOLDER_TITLE`, `Layout`, `LAYOUTS`, `layout_for`, `WdbQuest.conditional`), `pipeline/wfj/io/wago.py` (`read_ids`), `pipeline/wfj/cmd/import_.py` (`import english wdb`), `pipeline/wfj/cmd/import_english.py` (`run_wdb`, `_wdb_keyed_lines`, `_add_keyed`), `pipeline/wfj/dev/wdb_layout.py`, `pipeline/wfj/dev/cut_wdb_fixture.py`, `pipeline/wfj/io/git_store.py` (`load_english_at`), `pipeline/wfj/core/report.py` (`english_delta`, `render_delta`, `capture_rows`), `pipeline/wfj/cmd/stats.py` (`--delta`, `--capture`), `pipeline/wfj/cmd/generate.py` (`_pins_version`), the `Makefile` (per-client inputs, `wago-fetch`, `wdb-copy`, `wdb-preflight`, `client-preflight`, `import-shared-english`, `import-client`, `rebuild-check`), `tests/fixtures/wdb/`, `tests/fixtures/wdb-forever/`.
- **Date:** 2026-09-14
- **Amended by:** [ADR-054](054-quest-text-keyed-by-its-english.md), decision 11. A quest's conditional descriptions and its completion log line are now imported as English type `gossip`, keyed by the hash of their English, and the addon finds them by the live text.

## Context
Quest title / objectives / description English came from pfQuest (`pfquest@7786596`), a community database. ADR-019 measured it against Blizzard's own 1.15.9 text and found it differs on about 1% of quests. Each difference is a false stale marker for a correct translation, and a quest whose text Blizzard changed on Forever would not show up as changed at all.

The client keeps the text of quests it has seen in its quest cache, `Cache/WDB/enUS/questcache.wdb`. Progress / completion text is **not** in the cache; it stays VMaNGOS's (ADR-019).

Two constraints bound the design. The harvest is local pipeline tooling, never the addon ([principle 4](../architecture/principles.md#4-the-addon-never-ships-stored-english)). And the cache is imported straight into `data/english/quest` in ADR-019's per-field format, with no separate harvest folder to keep in step.

## Decision
1. **The cache format, as verified.** `io/wdb.py` reads `questcache.wdb` with the stdlib only. The framing below holds on every build seen; the **payload** offsets are pinned per build (decision 11). On Classic Era 1.15.9.69722, the 493,703-byte cache of the 1–500 scan holds 485 records, and the decoder consumes all 485 exactly.
   - Header, 24 bytes: magic `TSQW`, build `u32`, locale `SUne` (enUS reversed), then three `u32` the reader does not use.
   - Records: `[quest id u32][length u32][payload]`, ended by an 8-byte zero terminator.
   - Payload (1.15.9.69722): fixed fields; the objective count `u32` at 448; three list counts at 480 / 484 / 488 (always 0 on that build); a 12-byte bit block at 492 holding the byte lengths of nine strings (9·12·12·9·10·8·10·8·11 bits, MSB first, zero padding); the objectives from 504 (43 bytes each plus a description whose length is at +41; the flag byte at +42 has its low 7 bits zero); then the nine strings back to back, no NUL. The first three are title, objectives (log description) and description. The others (area description, portrait giver / turn-in text and name, completion log) are not fields in our model.
   - Text is Blizzard's raw template (`$B`, `$N`, `$G a : b;`). Normalization and hashing stay in the importer.
   - A record whose title matches `PLACEHOLDER_TITLE` is a stub. It is dropped and counted (63 of the 4,217 records on the full Classic Era cache, none with a translation). The rule, case-insensitive, is `^\s*(?:<[A-Za-z]+>|\[[^\]]*\])|^\s*reuse\s*$`: a leading `<TAG>` in any case (`<UNUSED>`, `<TEST> HEY MISTER WILSON!`, `<nyi> <TXT>…`), a leading `[…]` (`[Never used]`, `[DNT] Holiday Quests Tracker`), or a title that is only `REUSE`. Real titles containing "Test" ("Test of Lore") stay.
2. **Loud failure, no guessing.** `read_quests` raises `WdbError`, naming the file and the quest id, on: wrong magic; a locale other than enUS; a build with no pinned payload layout; a record past the end of the file; a missing terminator or bytes after it; a payload that does not reach the fixed part, names another quest, has a non-zero list count, non-zero padding bits or unknown objective flag bits; a payload not consumed exactly; a string that is not UTF-8; a quest id cached twice ([principle 5](../architecture/principles.md#5-every-translation-is-keyed-by-the-game)). A changed layout on a new build stops the import; it never imports misread text.
3. **Filling the cache.** The cache holds the quests the client has loaded. Filling it is the maintainer's step, done with tooling kept outside this repository; the import reads the file.
4. **The rescan list.** `wfj import english wdb FILE --build B --questv2 QuestV2.csv --missing PATH` prints the coverage of QuestV2 ids below 10,000 and of all QuestV2 ids, and writes the unanswered QuestV2 ids to PATH, one per line. That needs the import to succeed, which needs the build's payload layout. `io/wdb.read_ids` walks the record framing only and returns the build and the cached ids, so it answers on a build whose payload layout is not decoded yet. `read_quests` shares that walk, so the framing is read one way only.

5. **Precedence: Blizzard's cached text replaces pfQuest's.** The import writes `title` / `objectives` / `description` lines with `src wdb@<build>` through the source-owned merge (`merge_source`). It replaces earlier `wdb@` lines and any (id, field) it provides. So:
   - a cached quest's pfQuest line for that field is replaced;
   - under union (decision 12), a quest any cache answered is taken whole, so pfQuest does not fill a field the cache left empty;
   - uncached quests keep pfQuest's lines;
   - VMaNGOS progress / completion lines are untouched.

   `make import` and `make import-english` run the wdb import **after** `pfquest` and `vmangos`. Every curated English import is a source-owned merge, so the last one to provide an (id, field) owns it. Run earlier, pfQuest's merge would replace the cached lines.
6. **One pinned build per client.** `src` is `wdb@<build>`, and the build in the file's header must equal the numeric suffix of `--build`, or the import exits 1 before writing. `generate` refuses one source pinned at several versions among shipped lines that are not `stale`, except for a source two clients serve (`emit/schema.MULTI_VERSION_SOURCES`, which holds `wdb` alone; pfQuest is a repo at a commit and VMaNGOS a database snapshot, so two versions there is still a half-run import). `Data/Meta.lua` records every version of such a source, joined and sorted (`wdb = "1.15.9.69722+1.60.1.70009"`); the per-line `english.src` is exact in every case, which is what `stats --unseen-since` reads. A `stale` line keeps the hash and `src` it was checked against (sticky, ADR-003), so its version is history and does not pin; without that, bumping a build with any changed shipped line would fail `generate`. A client's build is bumped in the same PR as the regenerated data, as `VMANGOS_SHA` is (ADR-019).
7. **QuestV2 is the plan and the denominator.** `make wago-fetch` downloads ItemSparse, SpellName, GlobalStrings, ItemSubClass, SpellItemEnchantment and QuestV2 for a client's build from wago.tools. It is all or nothing: every table downloads to `<Table>.csv.part` and is validated; only when all succeed are they moved into place. An HTTP error, an empty body or an HTML body removes the `.part` files and fails the target with `wago-fetch: <table> failed at <build>; no CSV replaced` (or `… is empty or not a CSV …; no CSV replaced`). `wago-fetch` refuses a client whose tables come from the local archive ([ADR-021](021-client-tables-from-the-local-archive.md)).
8. **An English delta report.** `wfj stats --delta REF` compares `data/english/<type>` at a git ref (`io/git_store`, `git ls-tree` / `git show`; the git repo is the database, ADR-006) with the working tree, for quest / item / spell / ui / gossip: ids new, ids removed, lines changed per field. `--capture PATH` writes the **capture list**: one JSONL row per quest that is new or whose title / objectives / description changed, with its current title and the source of its progress / completion English (`null` = none). These are the quests whose turn-in text a player must see in-game.
9. **Reading the game folder.** Local tooling may read and copy `Cache/WDB/<locale>/*.wdb` from the Classic Era and Forever installs (`make wdb-copy WOW_DIR=…`, which keeps the previous copy as `questcache.wdb.prev`). It never writes, moves or deletes anything in the game folder. The addon never reads the cache; `test_addon_no_harvest.py` checks `addon/` for `questcache`, `Cache/WDB`, `GetQuestInfo` and `WFJQ=`. The tooling never launches the game.
10. **The shrink guard, `--dry-run` and the preflight.** A quest that holds `wdb@<same build>` English but is not in the cache at all means a wiped cache or the wrong install. `import english wdb` then exits 1 and writes nothing: `wdb: N quest(s) with wdb@<build> English are not in <file> (ids…): a smaller cache of the same build would delete their English. Copy the right cache, or pass --allow-shrink`. With `--allow-shrink` it proceeds and prints `quests with earlier wdb English not in this cache: N (their English deleted, --allow-shrink)`. Union (decision 12) is for a cache of a *different* build; a smaller same-build cache is still the wrong file. `--dry-run` runs every check (build, layout, shrink guard, QuestV2 coverage), prints the report with `[dry run: nothing written]`, and writes neither the store nor `--missing`. Every client in `CLIENTS` is preflighted (cache, QuestV2, Spell / ItemEffect, the wdb dry run, the `<src>@<build>` stamp, the client-text dry run) before the first import step, so a missing or bad input stops the target with nothing written, and a broken second client cannot leave a half rebuild. So `make import`, `make import-english` and `make data` require every client's local quest cache and QuestV2.
11. **The payload layout is pinned per build.** The numbers in decision 1 are 1.15.9.69722's. Forever 1.60.1.69913 moved the objective count (448 → 436) and the objectives (504 → 488), moved the string-length block from a fixed `492` to *after* the variable parts, changed the bits behind the nine lengths from `0` to `32`, and added four counted lists that Classic Era does not have: 12-byte entries before the objectives (count at `64`), 4-byte entries after them (count at `448`, the old objective-count slot), two conditional-text arrays (counts at `472` / `476`), and an inner list inside each objective record (count at its `+33`). Later Forever builds reuse those offsets. `io/wdb.Layout` holds one set of these per build in `LAYOUTS`, each carrying the evidence it was verified against, and `read_quests` picks by the build in the file's header.

    **An unpinned build is refused before any payload is read.** `layout_for` raises, naming the pinned builds and pointing at `python -m wfj.dev.wdb_layout <cache>`, which reports per pinned layout how many records it reads and the first it cannot. That tool names a winner only when exactly one layout reads **every** record; a layout that reads most of a cache is a layout we do not understand, and it exits 1. Pinning the winner for a new build is then a code change a person makes, with the record count as its evidence. The Classic Era and Forever layouts read **zero** of each other's records, so a wrong pick is loud rather than plausible. How Forever's numbers were derived and checked (every record consumed exactly; 1,233 of 1,245 already-held titles reproduced character for character, the 12 differences being Forever's own edits): [the layout note](../research/2026-09-18-forever-questcache-layout.md).

    **Conditional quest text is keyed by its English.** Forever serves a variant of a quest's description per `PlayerCondition`. Classic Era has none. `WdbQuest.conditional` carries them so the payload is fully accounted for (without them the record does not add up, and decision 2 would refuse the file). A variant cannot be keyed by `(quest, condition)`: the addon would have to evaluate the condition to know which variant the player is seeing. So `import english wdb` writes each variant, and each quest's completion log line, as English type `gossip` keyed by the hash of its English, and the addon finds it by the live text ([ADR-054](054-quest-text-keyed-by-its-english.md)).
12. **Both clients, side by side, imported under union.** The Forever cache holds only part of the quests QuestV2 lists, so a Forever-only import would drop thousands of quests from Blizzard's own text back to pfQuest's. The `Makefile` declares `CLIENTS := classic-era forever`, oldest first, and per client its build, table source and product. Each client's inputs live in their own folder, `$(INPUTS)/clients/<client>-<build>/`: its table CSVs with their `tables-source.txt` stamp, `questcache.wdb`, and the `missing.txt` its cache import writes. The shared inputs (predecessor repos, lineage, pfQuest, VMaNGOS, the UI sources) stay at the `INPUTS` root. The single-client targets (`wago-fetch`, `tables-extract`, `wdb-copy`) act on `CLIENT` (default `forever`). `import` / `import-english` run the shared English (pfQuest, VMaNGOS) once, then for each client in order its wdb, wago-ids, client-text and wago-ui imports, all `--merge union`: a `wdb` line this cache does not provide is kept at the build that served it. The later client (Forever) owns every (id, field) it provides; a line only Classic Era has keeps its `wago@` / `wdb@1.15.9.69722` src. Adding a client is one `CLIENTS` entry, its three variables and its folder.

## Consequences
- **Blizzard's text fixes pfQuest's mistakes.** On the 1–500 cache, pfQuest carried another quest's text for quest 172 ("Ambushed In The Forest"; Blizzard's is "Children's Week"), and quests 105 and 211 differ by one word in the description. Over the full Classic Era cache, 99.2% of descriptions match pfQuest.
- **Shipped Japanese can change status when Blizzard's text arrives.** A rename in the quest (quest 5047's title: pfQuest "…Finkle Einhorn…", Blizzard "Pip Quickwit, At Your Service!") turns a trusted line `rejected` (`alignment_failed`), and it shows the live English until corrected with Blizzard's names. A line where pfQuest had another quest's text turns `stale` (the player already saw the marker through the live check, ADR-019 §3). A line rejected against pfQuest's numbers can turn `stale` when Blizzard's text has the right number, and starts showing Japanese with the marker.
- **The caches are not reproducible from the repo.** Each is pinned only by its client's build; its content depends on scan history, and it lives only in the gitignored inputs folder. It cannot be downloaded, so each import is backed up with a `SHA256SUMS` file; without that file nobody can rebuild `data/english/quest`.
- **The rebuild is reproducible and checked.** `make rebuild-check` refuses a dirty `data/` or addon folder (deleting nothing), runs the preflight, empties `data/english/`, runs `make data`, and fails with the diff if anything under `data/` or the addon differs from `HEAD`. On a clean tree it prints `rebuild-check: data/ and addon/WoWForeverJapanese rebuilt byte for byte`. It needs both quest caches, restored from their backups and checked with `shasum -a 256 -c SHA256SUMS`.
- **Removed ids stay near zero in the delta.** pfQuest lines persist for quests the cache did not answer, so `stats --delta` rarely reports a removed quest. The import's `--missing` list is the "not answered" view.
- **Rollback.** The data-only rollback is reverting the data commit, which restores the old lines and baselines exactly (ADR-006). Dropping the wdb step and re-running `make import-english` does not restore pfQuest's text: `merge_source` replaces only keys pfQuest provides, so wdb-only keys keep their `wdb@` lines, and the preflight requires the cache anyway. To roll back without reverting: remove every `src` `wdb@` line from `data/english/quest`, remove the wdb step and the preflight from the targets, then `make import-english check generate`. Stale flags the import set are sticky either way.
- **Out of scope:** the other caches (creature, npc, gameobject, pagetext; names stay English), CASC extraction, and the cache's area description (for example "Scout the gazebo on Mystral Lake…"), which is not a field in our model. The DB2 tables come from the installed client ([ADR-021](021-client-tables-from-the-local-archive.md)), so the harvest does not depend on wago.

## Alternatives considered
- **The addon runs the scan or reads the cache**: rejected. The addon ships no English and no harvest code (ADR-002).
- **A separate harvest folder, imported later**: rejected. It would duplicate the English store; the cache goes straight into `data/english/quest` in ADR-019's format.
- **A string-region heuristic instead of a full decode**: rejected. Guessing where the strings start can misread text silently, and a misread cache would re-baseline or stale thousands of shipped lines.
