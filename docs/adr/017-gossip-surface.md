# ADR-017: The gossip surface: ScrollBox subscriber callbacks for rows, post-hooked measure widgets for heights, a collector gossip kind with NPC ids

- **Status:** Accepted for the parts confirmed in-game (see Consequences); the rest is checklist 3. Implemented in `UI/Gossip.lua`, `UI/QuestFrame.lua` (greeting prose), `UI/Render.lua` (`preview`, `createBanner`), `Core/Lookup.lua`, `Core/Collector.lua`, `Main.lua`, `UI/Slash.lua`, `pipeline/wfj/io/collector_dump.py`, `pipeline/wfj/core/model.py`, `pipeline/wfj/cmd/import_.py`, `pipeline/wfj/core/report.py`, `pipeline/wfj/cmd/stats.py`, `pipeline/wfj/cmd/check.py` / `cmd/validate.py` / `core/status.py` (gossip in `check`), `data/gossip/`.
- **Date:** 2026-09-14

## Context
The NPC talk window was the last content surface without a module. On Classic Era it is not the named `GossipGreetingText` / `GossipTitleButtonN` widgets the predecessor wrote: `GossipFrame.GreetingPanel.ScrollBox` is a `WowScrollBoxList` whose rows come from template pools and are reused in any order as the list scrolls or pages [verified: `Gethe/wow-ui-source@classic_era` 1.15.9.69722, `Blizzard_UIPanels_Game/Classic/GossipFrame.xml:34–86`, `Shared/GossipFrameShared.lua:119–294`]. Three things follow from the client source:

- **No writer to hook per row.** `GossipFrameSharedMixin:Update` builds a data provider (a TITLE element with `C_GossipInfo.GetText()`, dividers, quest rows, one OPTION element per `C_GossipInfo.GetOptions()` entry sorted by `orderIndex`) and calls `ScrollBox:SetDataProvider`; the row initializers are closures inside `UpdateScrollBox`. After a row's initializer the list view fires `OnInitializedFrame`, and `Release` fires `OnReleasedFrame` [verified: `Blizzard_SharedXML/Shared/Scroll/ScrollBoxListView.lua:384–397, 437–446`]. `ScrollUtil.AddInitializedFrameCallback` / `AddReleasedFrameCallback` are the subscriber API Blizzard documents for addons [verified: `ScrollUtil.lua:14–53`].
- **Extents come from measure widgets, and every row must be as tall as its extent.** The element extent calculator writes each element's text into one of four module-local measure widgets (`greetingTextFrame.GreetingText:SetText`, `titleOptionButton:Setup`) and reads `GetHeight()` [verified: `GossipFrameShared.lua:119–168`; `ScrollBoxLinearView.lua:154–240`]. A newly acquired row is sized to its extent (`ResizeFrame`, `ScrollBoxLinearView.lua:93–96`, called at `ScrollBoxListView.lua:369`); the view then lays out the visible rows by summing each frame's current `GetHeight()` (`LayoutInternal`, `ScrollBoxLinearView.lua:12–33`; `ScrollBoxViewUtil.SetPoint` returns `frame:GetHeight()`, `ScrollBoxViewUtil.lua:33–49`), and only then run the initializers. The extents also set the scroll range and the offset of the first visible row. A row resized after layout is not laid out again until the next layout pass. So a row whose Japanese wraps to a different line count than its English overlaps or leaves a gap unless its extent is measured on the Japanese.
- **The quest window's greeting prose** (`GreetingText`, written by `QuestFrameGreetingPanel_OnShow` from `GetGreetingText()`) is NPC dialogue with no id, which ADR-015 left untouched. The client reaches that writer through the panel's XML-bound `OnShow` and by name on `QUEST_LOG_UPDATE` [verified: `Classic/QuestFrame.lua:59–60, 99–104, 305–317`; `Vanilla/QuestFrame.xml:333–360, 497`].

ADR-005 fixed the gossip key (normalize_v1 + Hash32x2 of the live English) and promised a `wfj stats` listing of the highest-occurrence keys. ADR-013's collector had no gossip kind, so no gossip English existed anywhere.

## Decision
1. **Rows through the subscriber API, no writer hook.** `UI/Gossip.lua` (surface `gossip`, area and kind `gossip`) subscribes to `OnInitializedFrame` / `OnReleasedFrame` on `GreetingPanel.ScrollBox`: post-write callbacks, as ADR-009 anticipated for gossip. A TITLE row (button type 1) is recorded `greeting` on its `GreetingText` with the English from `C_GossipInfo.GetText()`; an OPTION row (type 3) is recorded `option.<orderIndex>` on `ButtonText.of(button)` with the English from `elementData.info.name`. Quest rows and dividers are never read or written. A row initialized while `GossipFrame` is not shown is never ours: the record is dropped and nothing is written. The client runs `Update` when `HandleShow` auto-selected a single option without showing the frame, and on `QUEST_LOG_UPDATE` while `hasActiveQuests` is stale. The ADR-009 equality guard applies: the row is shown only when the widget holds exactly the API English (a `GOSSIP_OPTION_PREPEND`-decorated option is left alone and any record on its key dropped); a widget still showing our text for the same English counts as ours. A released row's records are dropped before the pool hands the frame out again. `hooksecurefunc(GossipFrame, "Update", …)` records the greeting and every option to the collector (`UnitGUID("npc")`) and installs the measure hooks; `GossipFrame` `OnHide` releases the surface.
2. **Extents measured on what will be shown.** The first `Update` that finds the measure widgets (named in the data provider's elements) post-hooks them once per session: `hooksecurefunc(GreetingText, "SetText", …)` on the greeting measure FontString and `hooksecurefunc(optionButton, "Setup", …)` on the option measure button. Each hook (under a re-entrancy flag that is reset even when the body raises) resets the measure widget's original font, then, only when it shows exactly the API English, asks `Render.preview(surface, en, font, area, kind, id)` (the policy's desired text and font for an element with no record; no state touched) and writes that text and font into the measure widget (`Resize()` for the button), so the calculator's `GetHeight()` reads the height of the text the row will display and each row's extent equals the height it has after its initializer. Nothing is recorded on a measure widget. When the hooks are installed for the first time and any gossip record is applied, `ScrollBox:FullUpdate(true)` runs once, after the client's `Update` has returned, so the session's first window is laid out right. The refit (one closure per surface) resizes the recorded rows (`SetSize(270, GreetingText:GetHeight())` / `Resize()`) and calls `FullUpdate(true)` unless it is already inside a refit or inside the client's initializer callback.
3. **The gossip key is `Collector.key`, looked up over candidate keys.** `Collector.key(raw, player) = Hash.key(Normalize.v1(Collector.text(raw, player)))`: the text in Blizzard's tokens with the player's name, class and race (capitalized or lowercase, as quests) replaced. This **full key** is the collector's stored hash. `Collector.keys(raw, player)` (pure) returns the distinct candidate keys, most specific first: the full key, the name-only key (only the name replaced) and the key with nothing replaced. A line that says a class or race word literally ("the mage tower") gets the full key only for players of that class, so its data may be keyed either way. `Main`'s `gossipKey(text)` (injected into both surfaces as `deps.key`, and the key `/wfj debug gossip` prints) returns the first candidate with a shipped row (`Lookup.gossip`), else the full key; the Collector's gossip `known` check passes when a row is shipped under **any** candidate. Looking up several candidates cannot show another line's Japanese: every candidate is a hash of this same English. `Lookup.get("gossip", key)` delegates to `Lookup.gossip(key)`, so the Translator and the Collector read gossip through the one read path.
4. **A collector gossip kind that remembers its speakers.** `Collector.recordGossip(raw, guid)` is the kind's only entry point (`record` refuses `gossip` as `bad_kind`). Entry `gossip:<key>:text = { t = "gossip", i = key, f = "text", h = key, e, b, n = { creature ids } }`; gossip shares the quest checks (`TOKEN_KINDS = { quest, gossip }`: class and race required, `short_name`, `$N`/`$C`/`$R` tokens); `known` when `Lookup.get("gossip", key)` is non-nil. The same line from another NPC merges that creature id into `n` (sorted, unique, `NPC_CAP` = 32) and returns `seen`; a non-creature GUID adds no id. The import unions `npcs` on same-hash lines; `english_line` carries `npcs` on gossip only. `wfj stats` prints the **blast radius** after the coverage report: collected gossip keys, how many are translated, and the top 20 by NPC count. Listing collector gossip English there is not "consulting" it in ADR-013's sense (it builds no scope, changes no yield, no hash and no check), and collector English is the only gossip English there is; `check` / `validate` are unchanged.
5. **A marker banner on the gossip window, as on the quest window.** Markers are legible messages at the top of the window. The banner code is `Render.createBanner(frame, x, y, width) → fs, holder`: a holder frame raised `Render.BANNER_LIFT` = 10 levels above `frame`, a centred 14 px (`Render.BANNER_SIZE`) FontString in the bundled font and gold `WFJ.MARKER_COLOR`, hidden until a marker needs it; `UI/QuestFrame` calls it at TOP 0, −52, width 300. `UI/Gossip` creates its banner in `init` at TOP x +20, y −38, width 230 (`Gossip.banner` / `Gossip.bannerFrame`): centred right of the 61×61 portrait, in the stone band between the title bar and the parchment. Geometry [verified: `Gethe/wow-ui-source@classic_era` 1.15.9, `Blizzard_SharedXML/Classic/SharedUIPanelTemplates.xml` `PortraitFrameTemplateNoCloseButton`: 338 wide, TitleBg at y −3, Bg (rock) at y −21, portrait 61×61 top-left; `Blizzard_UIPanels_Game/Classic/GossipFrame.xml:37–42` `GossipFrameBg` parchment at TOPLEFT 7, −63; `:59–64` ScrollBox at y −65]. The only client widget in that band is `FriendshipStatusBar` (TOPLEFT 73, −41, 230×14, `GossipFrame.xml:73–77`), hidden unless `C_GossipInfo.GetFriendshipReputation` returns a friendship faction (`Classic/FriendshipStatusBar.lua:10–25`). `syncBanner()` runs before any row is measured or shown (in the measure hooks and `onInitialized`; `FriendshipStatusBar:Update` runs before `Update` on `GOSSIP_SHOW`, `Classic/GossipFrame.lua:14–17`): while the friendship bar is shown, `Render.setBanner("gossip", nil)` hides the banner and the markers fall back to inline; otherwise the stale / missing message is on the banner and the rows carry no inline prefix. `onUpdate` ends with `Render.updateBanner("gossip")`.
6. **The quest greeting prose is gossip on the quest window banner.** `UI/QuestFrame.lua` shows `GreetingText` as record `greeting` on surface `questframe.greeting`, area and kind `gossip`, refit `QuestGreetingScrollFrame:UpdateScrollChildRect()`, collector `recordGossip(GetGreetingText(), UnitGUID("questnpc"))`; the getter resolves through Compat (`greetingGetter`), and a client without it skips the prose (a `/wfj debug` unresolved line) while the greeting labels (ADR-015) still show. It is hooked on both client paths, `HookScript("OnShow")` on the panel and `hooksecurefunc("QuestFrameGreetingPanel_OnShow")` for the by-name call; a widget still showing our text for the same English is left as it is, so both hooks on one refresh write once. `questframe.greeting` joins the quest window banner; showing the greeting panel forgets the three quest panel surfaces, and a quest panel forgets `questframe.greeting`. Because the surface has the banner, a greeting label showing the missing marker (`marker.missing` on) shows it on the banner rather than inline, as the detail panels do.
7. **`wfj check` covers gossip.** `check.TYPES` gains `gossip`; `check.gossip_scopes(lines)` builds one `Scope(kind="gossip")` per line whose only English is the key itself (`hashes["text"] = id`, no English text), chosen by `check.scopes_for(english, store, type_)` in `check.run` and in `validate`'s referential rule. A gossip line gets only the Japanese check (Latin-only `text` → `not_japanese`), hand-written ranks before machine through the existing ranking and machine guard, and a passing line is `trusted`: never `unaligned`, and never `stale`, because changed English is a different key. `check` writes `english = {hash: <key>, src: "gossip-key@normalize_v1"}` (`check.GOSSIP_SRC`). This is the key, not collector English: ADR-013's "stored, not consulted" is unchanged.
8. **Gossip lines enter through the draft importer.** For example Conservator Ilthalaine's greeting in Shadowglen, "Ah, the beauty of Shadowglen never ceases to delight my senses!", key `db152bcd2f85b3f0`, enters with `make import-draft TYPE=gossip NAME=gossip-shadowglen MODEL=<model id> DATE=2026-09-14`: `ja` 「ああ、Shadowglenの美しさには、いつまでも心を奪われる！」 (the place name stays English, [principle 2](../architecture/principles.md#2-names-stay-in-english)), provenance `machine`, status `trusted`, in `data/gossip/gossip-db.jsonl` → `Data/Gossip/Gossip_db.lua`. A person can replace any such line with a `human` / `correction` variant, which wins (ADR-014).

## Consequences
- A line with no shipped row is untouched (no `SetText`, `SetFont` or `FullUpdate` on any gossip widget), and only its English is recorded with its NPC ids. Every shipped row renders with Alt for English and no code change.
- `make check` / `make validate` judge `data/gossip/` like any other type. A gossip line cannot go stale: once the English changes, the new key simply has no row (the collector then records it).
- Pool reuse cannot carry one row's text onto another: every record is keyed to its widget, dropped on release, and re-derived from the element data on the next initialize.
- Shared lines ("Goodbye.", "I would like to buy from you.") share one key and one Japanese line by design (ADR-005); the blast radius lists them first, so the lines a translation would change most widely are reviewed first.
- The collector file grows by ~20 bytes per NPC id on a gossip entry as the client writes it (`Collector.size` adds `16 + 20·#n` against `CAP_BYTES`), bounded by `NPC_CAP` = 32 per entry; the union across dumps in `data/english` is not capped, so the blast radius counts every NPC.
- **Candidate keys, residual:** data keyed from a dump by a player of the class or race the line names (a Mage's dump turns "mage tower" into `$C tower`) still misses for players of other classes, since no candidate of theirs replaces the word. An audit of imported dumps watches for such keys. A player whose name is under 3 code points never gets name substitution (ADR-005's minimum token length), so that player's full key equals the nothing-replaced key and the candidate list is shorter. Gender alias rows and short-name candidates: [ADR-024](024-gender-variants-and-short-name-candidates.md).
- **Greeting label markers** show on the quest window banner, not inline (Decision 6).
- Items to confirm in-game, [likely] until then: `UnitGUID("npc")` names the gossip NPC (checklist 3, the dump's `n`); `FullUpdate(true)` from our code after `Update` returns does not taint the list, and the gossip window works in combat (checklist 10); the ScrollBox, `ScrollUtil` and `C_GossipInfo` names match on Forever (checklist 11). If the measure hooks do not run, rows keep English-measured heights. Checklist 3 also confirms that the friendship-bar fallback shows inline markers.
- **The frame theme and our font.** Both gossip row initializers call `self:RegisterFontString(<row text>)` before `Setup`, and `GossipFrameSharedMixin:Update` ends with `self:UpdateTheme()` after `SetDataProvider` (`GossipFrameShared.lua:143, 148, 293`). `GossipFrame` is a `UIThemeContainerFrame`, a native type with no FrameXML source, so whether the theme re-applies a font object after our write (Japanese rows would then show boxes instead of glyphs) cannot be read from the source. Fallback if boxes ever show: re-apply the bundled font from the `Update` post-hook, which runs after `UpdateTheme`.
- **Confirmed in-game (Classic Era 1.15.9):** Conservator Ilthalaine's greeting showed the Japanese in the bundled font with glyphs, wrapped to two lines, with the quest row below it at the right offset. This confirms the measure-widget post-hooks (the row's height followed the Japanese) and that `RegisterFontString` / `UpdateTheme` did not put a font object back over our write on opening the window. With the line removed and `marker.missing` on, the window showed `[未翻訳 / Not Translated]` on the banner in the stone band under the NPC name, clear of the portrait and the parchment, with the English greeting untouched (Decision 5). Still open: glyphs after scrolling and a `QUEST_LOG_UPDATE` rebuild, `UnitGUID("npc")`, combat.
- **Rollback:** revert the PR and re-release. A dump written by this build and loaded by an older addon loses its gossip entries on the next save (the older `load` drops unknown kinds); an older pipeline reports them `bad_kind`. No data migration.

## Alternatives considered
- **Wrap the view's element extent calculator** (replace it with one that measures the Japanese): measures the right text in one place, but replaces a Blizzard closure; the taint of an addon-supplied calculator would spread through every ScrollBox update it takes part in, including the in-combat ones. `hooksecurefunc` post-hooks and `ScrollUtil` callbacks keep our code outside the client's execution path. Kept as the fallback if the measure hooks do not run (checklist 3).
- **Accept English-measured extents**: no hooks, but a Japanese row's height then differs from its extent: an acquired row is sized to the English extent (its Japanese text may not fit), the scroll range and offsets follow the English, and a row resized to its Japanese after layout overlaps the next row or leaves a gap until the next layout pass.
- **Write the Japanese into `elementData`** (the provider's text / `info.name`): the calculator and initializers would see it for free, but the element data is what the client reads its English from; the equality guard, Alt-for-English and release would all lose the live English (ADR-002).
- **Hook the named widgets the predecessor wrote** (`GossipGreetingText`, `GossipTitleButtonN`): they do not exist on Classic Era 1.15.x.
- **Inline markers on the gossip window** (the message on its own line above the row text): markers are legible messages at the top, as on the quest window. Inline markers are kept only as the fallback while the friendship bar holds the band.
- **Key gossip by NPC id + option index**: rejected in ADR-005 (options reorder with quest state); `option.<orderIndex>` is only a render record key, never a translation key.
- **Record gossip through `Collector.record(kind, id, …)`**: gossip has no game id; a separate entry point keeps `record`'s id checks strict for the numeric kinds.
